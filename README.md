test3(img2model) 카탈로그가 만든 3D 캐릭터로 굴러가는, Godot 4.7 3D 액션 로그라이크.

하나 고르고, 상인에게 금화를 씁니다. 죽으면 처음부터입니다.

```

```

### 판을 영상으로 남기기

제목 화면에 **버튼이 둘**입니다 - `내려가기` 와 `● 녹화하며 내려가기`. 뒤엣것을
누르면 그 판이 소리까지 함께 영상으로 담기고, 끝나면 화면 위에 저장 판이 떠서
`공유하기` 한 번으로 카톡·메시지 공유창이 그대로 열립니다.

![녹화 중](out/screenshot_record.png)

켜고 끄는 스위치가 아니라 시작 버튼을 하나 더 둔 이유는, 스위치면 시작하기
전에 **지금 켜져 있는지 확인하는 일**이 늘 붙기 때문입니다. 버튼이 둘이면 누르는
순간 정해집니다. 녹화는 그 한 판만입니다 - 죽고 다시 도전하면 녹화하지 않습니다.
그러지 않으면 방금 남긴 영상이 새 녹화에 덮여 사라집니다.

| | |
|---|---|
| 한도 | 2분 또는 64MB. 먼저 닿는 쪽에서 자동으로 끝냅니다 |
| 화질 | 화면 그대로, 30fps, 2.5Mbps (2분에 40MB 남짓) |
| 형식 | mp4(H.264+AAC) 를 먼저 씁니다. 안 되는 브라우저만 webm |
| 끝나는 때 | 쓰러졌을 때 · `여기까지 저장` 을 눌렀을 때 · 한도에 닿았을 때 |

![저장 판](out/screenshot_record_save.png)

**보내는 길과 남기는 길을 둘 다 둡니다.** `공유하기` 는 공유창을 열어 카톡·메시지로
바로 보내고, `내려받기` 는 파일로 떨어뜨립니다. 폰에서 "저장" 이 어디로 가는지는
기기마다 달라서 판에 한 줄 적어 뒀습니다 - 안드로이드·PC 는 내려받기가 곧 파일이고,
아이폰에서 사진첩에 넣는 길은 공유창의 `비디오 저장` 입니다.

내려받기 링크에 `target=_blank` 를 답니다. `download` 를 무시하고 **그 자리에서
영상으로 넘어가 버리는** 브라우저가 있는데(구형 iOS), 그러면 게임이 통째로
날아갑니다. 새 창을 지정해 두면 최악이라도 옆 탭에서 열립니다. 미리보기에 재생
막대를 단 것도 같은 이유입니다 - 전체화면으로 키워 길게 눌러 저장하는 길이 하나
더 생깁니다.

**mp4 를 먼저 고르는 것이 중요합니다.** webm 은 아이폰에서 재생이 안 되는 일이
흔해서, 보낸 사람은 멀쩡한데 받은 사람만 검은 화면을 봅니다.

#### 엔진이 아니라 브라우저가 찍습니다

엔진에도 녹화가 있지만(`--write-movie`) 데스크톱 실행 파일을 명령줄 옵션과 함께
새로 띄워야 하고, 결과는 PC 안의 폴더에 떨어집니다. **이 게임을 실제로 하는 곳은
폰의 브라우저입니다.** 거기서는 그 길이 통째로 막혀 있습니다.

브라우저에는 필요한 것이 이미 다 있습니다 - 화면은 `canvas.captureStream`, 묶는
것은 `MediaRecorder`, 보내는 것은 `navigator.share`. `scripts/recorder.gd` 가 하는
일은 이 셋을 잇고 게임 쪽에 버튼을 내는 것뿐입니다.

**소리는 따로 끌어옵니다.** `captureStream` 은 그림만 줍니다. 그래서 내보낸 HTML
머리(`export_presets.cfg` 의 `head_include`)에 심어 둔 스크립트가
`AudioNode.connect` 를 감싸 **스피커로 가는 노드를 전부 적어 둡니다.** 녹화를
시작할 때 그 노드들을 녹음용 갈래에 한 번 더 이어 붙이면 소리가 파일에도
들어갑니다. 이 스크립트는 엔진이 오디오 그래프를 만들기 **전에** 돌아야 하므로
프리셋에서 빼면 안 됩니다 - 빼도 녹화는 되고, 소리만 조용히 사라집니다.

#### 저장·공유 버튼만 게임 UI 가 아닙니다

`navigator.share` 는 **사용자가 방금 누른 그 순간에만** 열립니다. 엔진의 버튼은
브라우저 이벤트가 끝나고 다음 프레임에 눌린 것으로 처리돼서, 거기서 부르면
브라우저가 "사용자 동작이 아니다" 라며 거절합니다. 그래서 녹화가 끝나면 HTML
쪽에 진짜 버튼을 띄웁니다. 게임 화면 **위쪽**에 뜨는 것은 아래 절반이 조이스틱과
버튼 자리라서입니다 - 거기 띄우면 판을 닫기 전까지 조작이 막힙니다.

### 왜 조준 스틱을 안 만들었나

데스크톱은 이동(WASD)과 조준(마우스)이 분리돼 있습니다. 그대로 옮기면 폰에서는
엄지 두 개로 스틱 두 개를 굴려야 하는데, 근접 공격 게임에서 그 정밀도는 재미로
이어지지 않습니다. 대신 자동 조준을 넣어, 폰에서 정하는 것을 **어디로 움직일지**와
**언제 때리고 언제 구를지** 로 좁혔습니다 - 원래 이 게임의 재미가 거기 있습니다.

### 아이폰에서 주소창 없이

Safari 에서는 버튼으로 전체화면을 띄울 수 없습니다. iPhone 은 `<video>` 말고는
`requestFullscreen` 을 허용하지 않기 때문입니다(iPad 는 됩니다).

대신 **홈 화면에 추가**하면 주소창 없이 뜹니다.

```
공유 버튼 -> 홈 화면에 추가 -> 생긴 아이콘으로 실행
```

Godot 이 내보내는 HTML 에는 이걸 켜는 메타가 없어서, 그대로 두면 홈 화면에서
열어도 Safari 껍데기째 열립니다. `export_presets.cfg` 의 `html/head_include`
로 넣었습니다.

```html
<meta name="apple-mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-status-bar-style" content="black">
```

상태바를 `black`(불투명)으로 둔 이유는 노치 때문입니다. `black-translucent` 로
하면 화면을 한 뼘 더 쓰지만 가로로 들었을 때 노치가 HUD 위로 올라옵니다.

서비스 워커(PWA 오프라인 캐시)는 **켜지 않았습니다.** 아이폰에서 켜면 빌드를
새로 올려도 옛것이 계속 뜨는 일이 생기는데, 지금처럼 자주 고치는 동안에는
그게 더 성가십니다. 안드로이드 설치나 오프라인 실행이 필요해지면
`progressive_web_app/enabled` 를 켜면 됩니다.

그대로 남습니다.

#### 그림을 한 단계 물러나게 하기 (`stylize`)

원본은 한 장으로 보는 삽화입니다. 그대로 깔면 **어두운 얼룩이 타일마다
되풀이되고**, 무늬가 캐릭터보다 자세해서 눈이 바닥으로 갑니다. 배경은 캐릭터
보다 한 단계 물러나 있어야 합니다.

| 손잡이 | 무엇을 |
|---|---|
| `flatten` | 넓이의 12% 로 흐린 판으로 나눠 **큰 얼룩**을 지웁니다. 붓질은 그보다 작아 살아남고 넓게 진 그늘만 사라집니다 |
| `detail` | 잔무늬를 남길 비율. 흐린 판과의 차이를 줄여 깎습니다 |
| `lift` | **어두운 쪽만** 끌어올립니다. 되풀이가 눈에 띄는 건 결국 대비라, 검은 점이 옅어지면 같은 무늬라도 덜 도드라집니다 |
| `tone` | 밝기에 따라 **따뜻한 두 색 사이**로 모읍니다(그레이디언트 맵) |

`tone` 이 핵심입니다. 채도만 낮추면 따뜻함까지 같이 빠져 베이지-회색이 됩니다
(실제로 그렇게 나왔습니다). 진한 곳은 나뭇빛, 옅은 곳은 크림색으로 모으면 색은
하나로 정리되면서 따뜻함은 남고, 원본의 초록 이끼 얼룩처럼 튀는 색이 흡수되는
효과도 같이 옵니다 - 되풀이가 가장 먼저 눈에 띄던 것이 그 얼룩이었습니다.

`lift` 도 처음에는 전체에 더했다가 중간톤까지 떠서 나무색이 모래색이 됐습니다.
어두운 쪽만 올리도록(세제곱) 바꿔서 해결했습니다.

#### 되풀이는 결국 타일 크기

그림 처리로 얼룩을 지워도, 한 화면에 같은 그림이 서너 장 들어가면 되풀이는
보입니다. 바닥 타일을 6m x 3m 에서 **7.5m x 4.5m** 로 키워 한 화면에 한 장
남짓만 들어가게 했습니다. 덤으로 무늬가 1.6배 커져 캐릭터 옆에서 덜
자잘해집니다.

끝까지 키우지는 않았습니다. 10.5m x 6m 까지 가 봤더니 판자 한 장이 어른 키만
해져서 아이가 거인의 마루에 선 것처럼 보였습니다.

#### 벽은 아틀라스로

벽 그림 하나를 반복하면 복도 내내 같은 액자가 걸립니다. 액자 벽·시계 벽·민무늬
둘을 **한 장(2048x272)** 으로 이어 붙이고, 벽 칸마다 자리 해시로 넷 중 하나를
고릅니다. 재질은 하나라 드로우 콜이 늘지 않습니다.

민무늬가 둘인 게 중요합니다. 액자와 시계가 절반씩 나오면 그것도 결국 벽지처럼
보입니다 - 실제 방도 대부분의 벽은 비어 있고 가끔 뭐가 걸려 있어서, 그 비율이
"가끔 눈에 띄는 것"을 만듭니다.

윗면과 옆면은 분리했습니다. 내려다보는 카메라라 벽 윗면이 가장 많이 보이는데,
거기에 액자가 깔리면 벽이 바닥처럼 보입니다. 윗면은 단색, 옆면만 그림입니다.

### 폰트에 없는 글자

`tools/make_font.py` 는 소스의 문자열에 나오는 글자만 남긴 한글 폰트를 만듭니다.
여기에 함정이 하나 있었습니다 - **서브셋은 원본에 없는 글자를 조용히 넘어갑니다.**
맑은 고딕에는 `♦`(U+2666) 가 없어서 금화 아이콘이 폰에서 계속 빈 네모였는데,
데스크톱에서는 OS 가 다른 글꼴로 대신 그려 줘서 눈치채지 못했습니다.

이제 원본에 없는 글자를 찾으면 목록을 찍습니다. `♦`→`◆`, `−`→`–`, `✦`→`★`,
`▭`→`■` 로 바꿨습니다.

### 따뜻한 색으로 — 조명

에셋이 전부 수채화라 조명도 그쪽에 맞췄습니다. 원래는 푸른 지하실이었습니다.

| | 전 | 후 |
|---|---|---|
| 해 | `(0.72, 0.76, 0.95)` 푸른빛 | `(1.00, 0.93, 0.78)` 아이보리 |
| 환경광 | `(0.46, 0.44, 0.52)` 보랏빛 | `(0.62, 0.56, 0.46)` 따뜻한 회갈색 |
| 안개 | `(0.07, 0.06, 0.09)` 남색 | `(0.24, 0.19, 0.14)` 갈색 |
| 방 안의 등 | 2.6 | 2.0 |
| 칸별 밝기 흔들기 | 0.22 | 0.10 |

안개 색이 특히 큽니다. 푸른 안개는 차가운 지하실이 되고, 따뜻한 갈색 안개는
저녁 빛이 도는 실내가 됩니다.

칸별 밝기 흔들기를 줄인 것은 그림이 깔린 뒤로는 세게 흔들 이유가 없어서입니다.
무늬가 이미 변화를 주고 있는데 밝기까지 흔들면 바닥이 얼룩덜룩해집니다.

### 규약 차이 두 가지

넣자마자 캐릭터가 **바닥에 누워 있었습니다.** 추측 대신 GLB 의 정점 경계를
직접 재 보니 머리가 `z = -1.5`, 발이 `z = 0` 이었습니다. 위쪽 축이 `-Z` 라는
뜻입니다. 그리고 세우고 나니 정면이 `+Z`(유니티 규약)라 Godot 의 앞(`-Z`)과
반대였습니다.

두 회전을 노드 하나에 몰면 오일러 적용 순서에 걸려 결과가 헷갈리므로,
`scripts/models.gd` 에서 **바깥 노드가 방향, 안쪽 노드가 세우기**를 맡습니다.
게임의 나머지 코드는 전부 Godot 규약만 씁니다.

### 팔 본이 어긋났던 이야기

처음 받은 도원 리그는 **팔 본이 메시와 어긋나 있었습니다.** `LeftArm` 이
`(-0.086, 0.84)` 에서 `(-0.116, 0.578)` 로 거의 수직으로 내려가는데, 메시는
A 포즈라 팔이 옆으로 벌어져 있었습니다.

원인은 test3 의 랜드마크 검출이었습니다 - 손목 높이를 `어깨높이 − 키의 30~42%`
로 **하드 클램프**하는데(`landmarks.py`), 이는 팔이 아래로 늘어진 캐릭터를
가정한 값입니다. A 포즈에서는 손목이 어깨 높이 근처에 있어야 하는데 몸통
아래로 끌려 내려갑니다. 그래서 팔 본에 붙은 것이 팔이 아니라 셔츠였고, 걷기
동작을 얹으면 상체가 납작한 치마처럼 뭉개졌습니다.

**다시 리깅한 셋은 팔 본이 실제 팔을 따라갑니다.** 실측(`tools/probe_rig.py`)
으로 확인했습니다.

| 리그 | LeftArm head -> tail | 판정 |
|---|---|---|
| 도원(처음) | `(-0.086, 0.84)` -> `(-0.116, 0.578)` | 아래로 늘어짐 - 불일치 |
| 도원(다시) | `(-0.090, 0.826)` -> `(-0.241, 0.779)` | 옆으로 뻗음 - 일치 |
| 적1_박치기 | `(-0.074, 0.854)` -> `(-0.246, 0.789)` | 일치 |
| 적3_던지기 | `(-0.074, 0.799)` -> `(-0.244, 0.759)` | 일치 |

그래서 지금은 다른 캐릭터들과 같은 길 - test3 의 절차적 걷기 사이클을 리그에
얹는 방식 - 로 돌아왔습니다(`tools/make_kids.py`).

#### A 포즈를 차렷으로

리그의 기본 자세는 A 포즈입니다. 리깅에 좋은 자세이지 서 있는 자세가 아니라서,
그대로 두면 아이가 팔을 벌린 채 뛰어다닙니다. 모든 프레임의 어깨 각도에 상수
(-38도)를 더해 팔을 내렸습니다 - 걷기의 팔 흔들기는 로컬 X 축이고 벌림은
로컬 Z 축이라, 흔들기를 살린 채 벌림만 줄일 수 있습니다.

**끝까지 붙이지는 않습니다.** 처음에는 -55도로 차렷에 가깝게 만들었는데,
원본 A 포즈가 수평에서 17도밖에 안 내려온 자세라 55도를 더하면 팔이 거의
수직이 되어 **몸통을 파고듭니다.** 38도면 겨드랑이가 조금 열린 A 포즈로
남아서, 팔이 몸 속에 들어가지 않고 실루엣에서도 팔이 팔로 읽힙니다.

같은 처리를 어긋난 리그에 했을 때는 셔츠가 뭉갰습니다. 리그가 맞으니 이제
그냥 됩니다.

### 동작 네 가지

몸통 층이 만드는 것들입니다. 관절이 없으니 **실루엣과 리듬**으로 구분되게 했습니다.

| 동작 | 어떻게 |
|---|---|
| 걷기 | 한 걸음마다 오르내리는 반동 + 좌우 흔들림 |
| 달리기 | 속도가 최고 속도의 45%를 넘으면. 반동이 커지고 앞으로 더 숙입니다 |
| 구르기 | **앞구르기.** 허리를 축으로 한 바퀴 - 웅크렸다 펴고, 가는 쪽을 보고, 바닥에 붙었다 일어섭니다 |
| 고함 | **고개를 젖히고 허리를 굽히고 두 팔을 뒤로.** 앞으로 퍼지는 파문 세 겹 |

![외치기](out/screenshot_shout.png)
![고함 자세](out/screenshot_shout_pose.png)

무기가 없는 아이라 주 기술을 **소리 지르기(고함)** 로 잡았습니다. 화면과 도움말의
조작 이름도 `공격` 이 아니라 `고함` 입니다 - 무엇을 하는지가 이름에 있어야 합니다. 파문의 방향과 거리가
판정 범위(정면 110도, 2.7m)와 같아 눈으로 사거리를 배울 수 있습니다.

파문의 **크기는 그 범위에서, 시간표는 목소리 클립에서** 끌어옵니다. 가장 앞선
고리의 지름이 사거리(2.7m)와 같아지도록 커졌다가(`RING_SPAN`), 같은 자리로 다시
오므라들며 사라집니다. 목소리(`shout_a1.wav`)는 1.05초인데 0.05~0.90초 내내 최대치
근처로 울립니다(50ms 창 RMS 실측: 0.30~0.45초가 최대, 0.95초에 -20dB). 그래서 첫
고리가 가장 커지는 때를 0.32초에, 마지막 고리가 사라지는 때를 0.94초에 맞췄습니다 -
예전에는 0.55초에 다 사라져서 **목소리가 한창일 때 화면이 비어 있었습니다**.

자세는 본 층(`PoseOverride.SHOUT`)이 냅니다 - 고개를 젖혀 목을 열고, 허리를 접어
배에 힘을 주고, 팔은 그 반작용으로 뒤에 남습니다. 셋이 한 벌이라야 자세로
읽힙니다: 고개만 젖히면 하늘을 보는 것, 허리만 굽히면 배가 아픈 것이 됩니다.
팔은 **손 위치를 재서** 잡았습니다. 내려다보는 카메라에서는 팔이 몸에 가려
앞뒤가 구분되지 않아, 스크린샷만 보고 한 번은 앞으로 뻗어 두었습니다. 손 본에
앵커를 붙여 조준 방향으로 투영해 보니(양수가 앞) 어깨 X 가 -100 일 때 -0.173 로
가장 뒤였습니다(+90 은 +0.272 로 정반대). 팔꿈치는 편 채(0)가 가장 멀리 갑니다.

그런데 가장 뒤로 가는 자세는 **두 손이 등 뒤에서 모입니다**(간격 0.064m) -
팔이 뒤로 가면서 안쪽으로도 감기기 때문입니다. 벌어져야 내지르는 자세로
읽히므로 세 축을 같이 훑었습니다.

| 어깨 X / Y / Z | 뒤로 | 높이 | 손 간격 |
|---|---|---|---|
| -100 / 0 / 34 | -0.166 | 0.817 | 0.064 |
| -75 / 0 / 34 | -0.169 | 0.797 | 0.277 |
| -75 / 15 / 50 | -0.137 | 0.700 | 0.345 |
| **-75 / 45 / 50** | **-0.091** | **0.728** | **0.561** |
| -75 / 55 / 50 | -0.071 | 0.750 | 0.621 |

X 를 -100 에서 -75 로 줄이면 팔이 덜 올라가면서 벌어지고, Z(50)가 높이를 마저
내리고, Y(45)가 손끝을 바깥으로 돌립니다.

간격의 기준은 **팔 길이**입니다. 이 아이는 어깨에서 손끝까지 0.317m, 어깨
사이가 0.194m 인데, 손 간격이 팔 길이보다 짧으면 등 뒤에서 손을 맞잡은 것처럼
보입니다. 0.561m 는 팔 길이의 1.8배, 어깨 폭의 2.9배입니다. 벌릴수록 뒤로는 덜
가지만(0.137 -> 0.091) 벌어지는 쪽을 골랐습니다 - 뒤로 간 것은 옆에서만
보이고 벌어진 것은 어느 각도에서도 보이는데, 이 게임은 위에서 내려다봅니다.

지르는 동안 **이동 속도는 20%** 입니다. 눌리는 구간은 판정 시간(0.30초)까지만
입니다 - 자세를 붙잡는 0.62초나 목소리 1.05초까지 끌면 재사용 대기(0.55초)보다
길어져, 연타하면 발이 계속 묶입니다.

자세는 판정(0.30초)보다 긴 **0.62초**를 붙잡습니다 - 파문과 같은 이유로,
목소리가 아직 나는데 아이만 차렷으로 돌아와 있으면 어긋나 보입니다. 목소리
끝(1.05초)까지 끌지는 않았습니다. 팔을 1초 내내 뒤로 둔 채 뛰면 그건 고함이
아니라 달리는 자세입니다.

어깨 본의 부호는 **화면으로 확인했습니다**. 다른 자세들과 반대로 이 어깨는
양수가 뒤였습니다(A 포즈 쉬는 자세의 축이 본마다 다릅니다). -54 와 +54 를
나란히 찍어 골랐고, 고개(-21)도 같은 방법으로 확인했습니다. 몸통 노드가 내던
기울기는 0.6배로 줄였습니다 - 본이 허리 굽힘을 나눠 맡게 되어, 그대로 두면
둘이 더해져 몸이 반으로 접힙니다. 커지기만
하고 사라지면 소리가 끊긴 것으로 느껴지고, 크기가 범위와 무관하면 눈금 노릇을
못 합니다. 세 겹은 시차·크기·출발 위치를 조금씩 달리해 앞으로 벌어지게 뒀습니다 -
크기까지 같으면 셋이 겹쳐 하나로 보입니다(실제로 그렇게 나왔습니다).

![구르기](out/screenshot_roll.png)

구르기는 회전축이 중요합니다. 몸통 노드를 허리 높이에 두고 모델을 그만큼 내려
달았습니다 - 발을 축으로 돌리면 앞구르기가 아니라 발목을 축으로 한 재주넘기가
됩니다.

**회전 부호는 눈으로 고르지 마세요.** 70도로 내려다보는 카메라에서는 앞구르기와
뒤구르기가 거의 구분되지 않습니다. `--pose=roll --trace-at=1` 로 머리 본의
진행방향 거리를 찍어 판정합니다.

```
앞구르기 (-TAU)                뒤구르기 (+TAU)
t=0.05  머리 0.85  앞 +0.14     t=0.05  머리 0.84  앞 -0.15
t=0.26  머리 0.23  앞 +0.28     t=0.16  머리 0.53  앞 -0.32
t=0.47  머리 0.05  앞 -0.12     t=0.36  머리 0.05  앞 -0.08
t=0.68  머리 0.40  앞 -0.30     t=0.68  머리 0.42  앞 +0.30
```

머리가 **먼저 앞으로(+)** 숙였다가 바닥을 지나 뒤로 올라오면 앞구르기입니다.

### 옵션 메뉴

그 안에 카툰 켜기와 시야 각도가 있습니다. 항목을 화면에 늘어놓으면 옵션이
늘 때마다 HUD 를 잠식하는데, 폰에서는 그 자리가 곧 화면이라 더 그렇습니다.

| 항목 | 무엇을 | 키 |
|---|---|---|
| 카툰 | 카툰 렌더링. **기본이 켬입니다** - 에셋이 전부 수채화라 사진처럼 그리는 쪽이 오히려 어긋납니다 | `T` |
| 시야 | 내려다보는 각도를 40~78도에서 4도씩. **거리는 안 바뀌므로 캐릭터 크기는 그대로**이고, 벽에 가리는 정도만 달라집니다 | `[` `]` |

**메뉴가 열려 있는 동안에는 터치 버튼을 감춥니다.** 판이 오른쪽 위에 열리는데
상호작용 버튼이 그 아래에 있어, 판이 버튼을 덮으면 화면은 눌리는데 아무 일도
일어나지 않습니다. 자리를 옮겨 피할 수도 있지만 옵션이 하나 늘 때마다 다시
어긋납니다.

시야에서 거리를 같이 바꾸지 않는 것이 중요합니다. 거리까지 움직이면 각도를
조절할 때마다 캐릭터가 커졌다 작아져서, 내가 무엇을 조절하고 있는지 알 수
없게 됩니다.

#### 잡기 — 한 번 눌러 잡고, 다시 눌러 던집니다

던진 물건은 **날아가는 동안 못 잡습니다.** 손을 떠난 지 얼마 안 돼 아직 몸
옆에 있어서, 그대로 두면 던지자마자 도로 잡혔습니다 - 던진 것이 아니라
손에서 튕겼다 돌아온 것으로 보입니다. 느려져서 굴러다니는 물건이 되면 그때
다시 잡힙니다.

| 조작 | 결과 |
|---|---|
| 누름 (옆에 소품) | 그 자리에서 집습니다 |
| 누름 (앞에 적) | **손을 뻗고 달려듭니다** - 닿는 순간 갈립니다 |
| 들고 있을 때 다시 누름 | 던집니다 |

![달려들어 밀기](out/screenshot_lunge.png)

*손을 뻗는다 -> 달려간다 -> 닿는 순간 판정.*

#### 누르는 순간이 아니라 닿는 순간에 정합니다

예전에는 **누르는 그 프레임에** 판정했습니다. 사거리 안이고 등 뒤면 잡히고,
아니면 제자리에서 헛손질이었습니다. 무엇이 일어날지가 눌러 봐야만 알 수
있었고, 이펙트(하얀 상자가 튀는 것)는 맞든 안 맞든 똑같이 나와서 화면만
보면 성공과 실패가 구분되지 않았습니다.

지금은 이렇게 갑니다.

1. 보고 있는 쪽 2.6m 안의 가장 가까운 적에게 **손을 뻗고 달려갑니다**
   (0.85초, **평소 달리는 속도 그대로**). 달려가는 동안 그 자세가 화면에
   보입니다.
2. 손이 닿으면 그 자리에서 **앞이냐 뒤냐**로 갈립니다 - 등 뒤면 잡고,
   앞이면 밉니다.

   닿았다고 보는 거리는 **두 몸의 반지름을 더한 값 + 손끝 여유 0.12m**
   입니다. 처음에는 `사거리 x 0.55 + 적 반지름` 이라 1.54m 였는데, 두 몸을
   합쳐도 0.42m(실측: 내 0.20 + 적 0.22)뿐입니다 - **몸 세 개가 들어갈
   거리에서 넉백이 터졌습니다.** 손은 허공을 지나는데 적이 날아갔습니다.
   지금은 0.5m 언저리, 즉 붙는 순간에 터집니다(실측: 21번 달려들어 11번
   닿고 2번 헛손질).
3. 밀기가 성공하면 그때 이펙트가 나오고, 적이 **살짝 밀려납니다**(6.5).

달려가는 사이에 적이 돌면 결과도 바뀝니다. 눈에 보이는 것과 일어나는 일이
같아졌습니다.

소품은 달려들지 않고 그 자리에서 집습니다. 물건에는 등 뒤랄 것이 없고,
발밑의 인형을 집으려고 몸이 튀어 나가면 그게 더 이상합니다.

앞에 아무도 없으면 제자리에서 한 번 밀칩니다 - 헛손질도 동작은 나가야 버튼이
먹은 것으로 느껴집니다. 다만 **이펙트는 안 나옵니다.**

#### 고치면서 드러난 셋

**다리가 안 움직였습니다.** 손만 뻗은 채 미끄러져 갔습니다.

두 겹이었습니다. 누를 때 밀기 클립을 틀었고, 그 클립이 도는 동안에는
`_drive_animation` 이 통째로 비켜섭니다(팔 동작이 걷기에 덮이면 안 되니까요).
클립을 안 틀도록 고쳤는데도 다리는 그대로 멈춰 있었습니다 - **`_push_time` 은
여전히 흐르고 있었고, 비켜서는 조건이 그 시간만 보고 있었기 때문입니다.**
달려드는 중에는 그 조건에서 빠지도록 해야 했습니다.

**너무 빨랐습니다.** 이동 속도의 2.4배(7.4m/s)로 튀어 나갔습니다. 달려가는
것이 아니라 쏘아지는 것이고, 다리도 그 속도를 못 따라가 배속이 한계에
걸렸습니다. **1.0배(평소 달리기 그대로)** 로 낮췄습니다 - 실측 3.10 m/s,
클립 배속 2.84 로 평소 달릴 때와 **같은 숫자**입니다. 그만큼 시간이 더
걸리므로(2.6m 를 0.85초) 사거리와 시간도 함께 맞췄습니다.

**적이 둘이면 두 번 나갔습니다.** 달려들 상대를 못 찾았을 때의 밀기가 사거리
안의 **모두**를 치고 있었습니다. 한 번 눌렀는데 둘이 같이 날아가니 기술이 두 번
나간 것으로 보입니다. 달려드는 쪽이 한 명을 고르는 기술이 됐으므로 이쪽도
한 명으로 맞췄습니다(실측: 누름 33회에 밀기 성공 7회 - 누른 수를 넘지 않습니다).

**버튼 이름과 자리.** `잡기` 만 적어 두면 밀기가 따로 있는 기술인 줄 압니다 -
한 버튼이고 앞이냐 뒤냐로 갈리므로 `밀기(잡기)` 로 바꿨습니다. 고함과 자리도
맞바꿨습니다: 붙어서 쓰는 기술이 더 자주 눌리는데 엄지가 가장 편한 아래쪽이
고함 차지였습니다. 글자가 길어져 둥근 버튼 밖으로 삐져나가길래, 이름이 길면
글자 크기를 줄이도록 했습니다.

예전에는 **누르고 있는 동안 들고, 떼면 던졌습니다.** 폰에서 그게 잘 안 됩니다 -
던지려면 한 엄지로 버튼을 누른 채 다른 엄지로 방향을 주고 버튼만 떼야 하는데,
스틱을 먼저 놓는 일이 잦아 그냥 발밑에 떨어집니다. 누름 하나로 통일하면 그
순서가 사라집니다.

방향이 없으면 **보고 있는 쪽으로** 던집니다. 발밑에 내려놓지 않습니다 - 누름
한 번으로 던지는 방식에서는 "던지려고 눌렀는데 놓였다" 가 실수로만 느껴집니다.

집자마자 던져지지 않도록 잡은 뒤 **0.30초**는 던지기가 막힙니다. 손에 붙는 것을
보고 나서 던질 수 있어야 "집었다 -> 던졌다" 가 두 동작으로 읽힙니다.

여기서 버그가 하나 있었습니다. **짧게 한 번 눌렀을 뿐인데 집자마자 날아갔습니다.**
누름이 대기(0.14초)에 걸려 큐에 들어갔고, 대기가 풀리는 순간 그 누름이
**던지기로 되살아난** 것입니다. 큐가 필요한 것은 "잡기/밀기가 대기 중이라 아무
일도 안 일어난" 경우뿐이라, 지금은 손에 든 것이 있으면 큐를 버립니다 - 던지기는
든 것이 눈에 보이니 안 되면 다시 누르면 되고, 기억해 뒀다가 나중에 던지면
오히려 놀랍니다.

![손에 들기](out/screenshot_hold.png)

**소품은 손에 붙습니다.** 오른손 본(`RightHand`)의 실제 위치를 매 프레임 읽어
따라가게 했습니다. 머리 위에 얹으면 밀기 동작에서 팔은 뻗는데 물건은 정수리에
붙어 있어 두 동작이 따로 놉니다. 본을 못 찾으면 몸 앞 허리 높이로 돌아갑니다 -
모델을 바꿨을 때 물건이 사라지는 것보다 낫습니다.

들고 있는 동안 소품은 **충돌 세계에서 빠집니다.** 들린 소품은 매 프레임 손
위치로 순간이동하는데, 얼린 강체는 정적 장애물이라 들고 있는 사람의 캡슐 안으로
순간이동하면 사람이 그것을 밀어내려다 옆으로 튕겨 나갑니다 - 큰 소품을 들면
캐릭터가 날아가는 것처럼 보이던 것이 이것입니다. 앞으로만 미는데 옆으로 밀리고
(x 41→42) 속도가 3.1 대신 0.7~2.0 으로 널뛰었습니다.

**적은 들지 않습니다. 등을 잡아 끕니다.** 아이가 또래를 번쩍 드는 그림은
어색하고, 무엇보다 잡는 순간 상대가 내 머리 위로 순간이동하면 잡았다는 느낌이
안 납니다. 잡혀도 **자리가 그대로**이고, 내가 멀어질 때만 목줄(1.05m)이
팽팽해지며 끌려옵니다. 늘 당기면 잡는 순간 홱 끌려와서 같은 문제가 됩니다.
끌리는 동안에는 잡은 쪽에 등을 보이고 버둥거립니다.

돌진형과 선생님은 잡히지 않습니다 - 관문이 끌려다니면 관문이 아닙니다.

##### 던지는 방향 — 스틱이 가리킨 쪽, 또는 화면 안의 적

두 가지를 고쳤습니다.

**스틱을 먼저 놓아도 던져집니다.** 던지려면 방향을 준 채로 잡기 버튼을 떼야
하는데, 엄지 두 개가 서로 다른 일을 하고 있어서 스틱을 먼저 놓는 일이
잦습니다. 그러면 방향이 없다고 판단해 그 자리에 툭 내려놓았습니다 - 던진 줄
알았는데 안 던져지는 것으로 느껴집니다. 조금 전(0.6초 안)에 가리킨 쪽을
기억해 두었다가 씁니다.

**화면 안의 적을 겨눴으면 그쪽으로 정확히 갑니다.** 예전에는 35도 안에서
65%만 당겨 줬는데, 그러면 적을 겨눴는데도 옆으로 스치는 일이 남습니다 -
반쯤 도와주는 것이 도와주지 않는 것보다 나쁩니다. 45도 안에 **화면에 보이는**
적이 있으면 끝까지 붙입니다. 화면 밖은 세지 않습니다 - 안 보이는 적에게
물건이 빨려 들어가면 내가 던진 것이 아니라 게임이 던진 것이 됩니다.

측정으로 확인했습니다:

```
입력 (+1.00, 0.00), 화면에 적 없음        -> (+1.00, 0.00) 그대로
입력 (+1.00, 0.00), 37도 옆에 적이 보임    -> (+0.80, +0.60) 적쪽으로 완전히
```

##### 던지기 — 감았다 뿌리기

뒤로 **15도** 느리게 감았다가, 가속하며 앞으로 **30도** 돕니다(0.22초). 앞으로
도는 30도 중 15도는 감은 것을 푸는 데 쓰이므로 던지는 방향을 15도 지나쳐
멈추고, 그 15도가 던지고 난 뒤의 여운이 됩니다.

처음에는 해머던지기처럼 **한 바퀴**를 돌렸는데 큰 문제가 있었습니다. 도는
동안 물건이 손에 붙어 몸 반대편까지 휘돌아 가서, **오른쪽으로 던졌는데 왼쪽에서
날아가는 것처럼** 보였습니다. 방향 자체는 맞았습니다 - 입력 +X 에 대해 실제
발사 방향도 (1.00, 0.00) 이었습니다. 눈이 속은 것은 물건이 떠나는 **자리**
였습니다.

두 가지로 고쳤습니다. 회전을 45도로 줄였고, 놓는 순간 물건을 **손 위치에 딱
붙입니다** - 들고 있는 동안에는 손을 조금 늦게 따라오게 해 두어서(손맛), 그냥
놓으면 아직 뒤쪽에 남아 있는 자리에서 날아갑니다.

##### 비거리 — 크기가 정합니다

작은 것은 멀리, 큰 것은 가깝게. 기준점 둘로 곡선을 맞췄습니다.

```
거리 = 2.5m x (1.25 / 크기) ^ 0.654
```

1층 적(키 1.25m)이 제 키의 두 배인 2.5m, 가장 작은 소품이 한 화면쯤인 10m 가
되는 곡선입니다. 실제로 나오는 값:

| | 크기 | 비거리 |
|---|---|---|
| 기차 | 0.16 | 9.7m |
| 담요·나뭇잎이불 | 0.18 | 8.7~9.0m |
| 별쿠션 | 0.36 | 5.7m |
| 장난감상자·고양이버스침대 | 0.39~0.40 | 5.3m |
| 아이의자 | 0.45 | 4.8m |
| 1층 적 | 1.25 | **2.5m** |

크기는 경계 상자 **부피의 세제곱근**입니다. 가장 긴 변으로 재면 납작한 담요가
기차보다 크게 나와서, 덩치와 상관없이 안 날아갑니다.

종류마다 손으로 적어 두던 `fly` 배수는 없앴습니다. 크기로 알 수 있는 것을
따로 적어 두면 모델을 바꿨을 때 반드시 어긋납니다.

**한 가지 걸립니다.** 담요와 나뭇잎이불이 이제 가장 멀리 날아갑니다(9m). 부피로
치면 실제로 작아서 규칙에는 맞지만, 이 둘은 맞은 적을 멈추는(stun) 소품이라
"멀리서 묶어 두기" 가 됩니다. 예전에는 가장 안 날아가는 것이었습니다. 원치
않으시면 부드러운 것만 거리를 깎겠습니다.

### 던진 것이 맞았을 때

물건도 적도, 날아가다 적에게 닿으면 피해를 줍니다. 여기 함정이 둘 있었습니다.

**높이를 같이 재고 있었습니다.** 적의 원점은 발밑인데 던진 물건은 1m 쯤 떠서
날아갑니다. 3D 거리 하나로 재면 **머리를 정통으로 지나가도** 원점까지는 1m 가
넘어 빗나간 것으로 처리됩니다. 이제 수평 거리와 높이를 따로 봅니다 - 수평으로
닿았고 발밑에서 키 사이의 높이에 있으면 맞은 것입니다.

**속도 문턱이 높았습니다.** 비거리를 크기로 정하면서 수평 속도가 예전 9 고정
에서 2~8 로 내려왔는데, 감쇠까지 걸려 날아가는 도중에 문턱 아래로 떨어졌습니다.
소품은 3.0 → **1.2**, 던져진 적은 4.0 → **2.0** 으로 내렸습니다.

`--pose=pitch` 로 확인합니다 - 표적을 세워 두고 소품과 적을 던져 체력이 닳는
것을 봅니다. 우연에 기대면 확인이 안 됩니다.

```
기차를 던져 맞힘      42 -> 8   (34 = 공격 20 x 던지기 1.5 x 기차 1.10)
적을 던져 맞힘        42 -> 31 -> 20   (11씩 = 그 적의 공격력 x 1.2)
```

### 부딪히기

주인공·적·소품이 서로 몸으로 부딪힙니다. 부딪힌 쪽은 조금 느려지고, 맞은
쪽은 밀려납니다.

`CharacterBody3D` 는 강체를 자동으로 밀지 않습니다. 그냥 두면 인형이 벽처럼
단단해서 발에 걸린 장난감이 사람을 막습니다. 그래서 미끄러짐 충돌을 훑어
부딪힌 강체에 충격을 넣고, 내 속도는 깎습니다.

**소품의 마스크에는 사람이 없습니다.** 사람이 소품을 미는 방향만 둔 것인데,
반대로 두면 발밑에 굴러온 인형이 플레이어를 벽으로 밀어 넣습니다. 적끼리도
부딪히지 않습니다 - 복도에서 서로 막혀 길이 잠기기 때문에, 그쪽은
`_avoid_crowd` 가 부드럽게 벌려 놓습니다.

#### 동작 크기 — 프레임마다의 각도를 그 자리에서

![동작 크기](out/screenshot_riglab_motion.png)

`다리 / 팔 / 상체 / 반동` 네 손잡이가 **프레임마다의 각도에 배율을 곱합니다.**

구운 클립은 회전 키의 나열입니다. 각 키를 쉬는 자세 기준으로 보면 그것이 곧
그 프레임의 각도이고, 거기에 배율을 곱하면 **리듬은 그대로 두고 크기만**
바뀝니다 - 어느 프레임에 가장 크게 벌어지는지는 건드리지 않습니다.

`프레임` 슬라이더로 한 지점에 세울 수 있습니다. 크기를 조절할 때는 같은
프레임을 놓고 비교해야 합니다 - 흐르는 동작에서는 매번 다른 순간을 보게 되어,
방금 바꾼 것이 좋아진 것인지 프레임이 달라진 것인지 알 수 없습니다.

두 번 틀리고 고쳤습니다.

- **항등 회전에서 slerp 로 섞었더니 1 을 넘겨도 안 늘어났습니다.** slerp 는
  사이를 채우는 것이지 밖으로 늘리는 것이 아닙니다. 축과 각도로 풀어서
  각도에만 곱하는 것으로 바꿨습니다.
- 그랬더니 이번엔 1.5배가 **210도**로 나왔습니다. `q` 와 `-q` 는 같은
  회전인데 w 가 음수로 들어오면 `get_angle()` 이 340도를 돌려줍니다 - 20도를
  30도로 늘리려다 340도를 510도로 돌린 것입니다. 짧은 쪽으로 돌려놓고
  곱하니 10 / 20 / 30도로 정확히 나옵니다.

재 보면 알게 되는 것도 있습니다. **다리 배율을 1.5배로 올려도 바닥을 미는
거리는 거의 그대로입니다**(0.393 -> 0.392). 같은 손잡이가 무릎도 같이 키워서,
허벅지가 더 벌어지는 만큼 정강이가 더 접혀 발이 도로 몸 쪽으로 옵니다.
0.5배로 줄이면 0.264 로 확실히 줍니다.

#### 고른 값을 굽기까지

`값 저장` 이 `assets/anim_tuning.json` 에 적고, `tools/make_kids.py` 가 구울 때
읽습니다. **파일 하나를 사이에 두는 덕에 미리보기와 굽기가 같은 값을 봅니다** -
화면에서 고른 숫자를 손으로 옮겨 적으면 언젠가 어긋납니다.

```json
{ "seojin": { "legs": 0.6, "arms": 0.6, "torso": 0.6, "bob": 0.6 } }
```

저장할 때 **곱해서 쌓습니다.** 슬라이더는 "지금 클립 대비" 배율이라, 한 번
굽고 나면 그 값이 클립에 들어가 슬라이더는 1.0 으로 돌아갑니다. 곱해 두면
파일에는 늘 원본 대비 총량이 남습니다.

굽는 쪽은 `press_arms` 보다 **먼저** 배율을 곱합니다. 그쪽은 팔을 몸에 붙이는
상수를 더하는데, 그것까지 같이 줄이면 팔이 도로 벌어집니다.

**미리보기와 구운 결과가 같아야 합니다.** 본의 쉬는 자세만 옮기면 살가죽이
따라 올라가 몸이 찌그러집니다. 오프라인 도구는 glTF 의 inverseBindMatrices 를
다시 계산해서 이것을 막는데, 런타임에도 같은 것이 있습니다 -
`Skin.set_bind_pose()` 가 그 행렬입니다. 실험실도 본을 옮길 때마다 바인드
자세를 새 쉬는 자세로 다시 계산하므로, **여기서 보이는 것이 구운 뒤에도
그대로** 나옵니다. 계산식도 `raise_hips.py` 와 같은 것을 씁니다 - 갈라지면
미리보기가 거짓말이 됩니다.

바닥 속도는 게임이 스케이팅을 없앨 때 쓰는 것과 **같은 자**입니다. 여기서 읽은
숫자를 `player.gd` 의 `WALK_GROUND` 에 그대로 옮겨 적을 수 있습니다. 배속으로
나눠 1배속 기준으로 환산하므로 배속을 바꿔도 같은 값이 나옵니다.

**이 화면은 GLB 를 고치지 않습니다.** 마음에 드는 값을 찾으면 `이 값으로 굽는
명령 찍기` 가 그대로 붙여 넣을 수 있는 명령을 찍어 줍니다. 게임이 에셋을 몰래
고치기 시작하면 무엇이 원본인지 알 수 없게 됩니다.

스킨은 GLB 에서 온 공유 자원이라 복제해서 씁니다 - 그대로 고치면 실험실에서
만진 것이 게임 안 캐릭터에까지 남습니다.

### 미끄러지지 않는 걸음 — 재생 속도를 이동에 맞춥니다

발이 바닥을 미는 속도와 몸이 나아가는 속도가 같아야 미끄러지지 않습니다.
예전에는 `속도 / 3.0 x 3배` 라는 손으로 맞춘 식이었는데, **재 보니 어긋나
있었습니다.**

발 본에 앵커를 붙여 몸 기준 로컬 좌표에서 뒤로 가는 발의 이동을 4초간
더했습니다(`run.bat --pose=stride`). 그것이 곧 그 클립이 1배속에서 약속하는
이동 속도입니다.

| 클립 | 길이 | 1배속에서 미는 속도 |
|---|---|---|
| 걷기 | 1.292초 | **0.644 m/s** |
| 달리기 | 0.958초 | **1.093 m/s** |
| 적1_박치기 걷기 | | 1.141 m/s |
| 적3_던지기 걷기 | | 0.994 m/s |
| 선생님 걷기 | | 1.304 m/s |

몸은 3.1 m/s 로 나가는데 걷기 클립은 0.36 m/s 를 밀고 있었습니다 - **발이
2.8배 미끄러지고 있었습니다.** 지금은 `배속 = 실제 속도 / 미는 속도` 입니다.

**달리기 클립을 새로 구웠습니다.** 정확히 맞추면 3.1 m/s 를 내는 데 걷기
클립은 8.6배가 필요합니다 - 다리가 보이지 않게 떨립니다. 보폭을 두 배로 키운
클립(다리 62도, 무릎 70도)을 따로 구워 4배로 낮췄습니다. 어느 클립을 쓸지는
"그 클립을 1배속으로 돌렸을 때의 속도" 로 가릅니다 - 달리기가 1배속을 넘기는
0.77 m/s 부터 달리기입니다.

적3_던지기(원거리 적)도 다시 구웠습니다. 같은 각도(31도)로 구웠더니 미는 거리가
적1_박치기의 1/3 밖에 안 나와서(0.124 m/s), 70도로 넓혀 0.282 로 올렸습니다.

**구르기 직후의 미끄러짐**도 같은 논리로 사라졌습니다. 예전에는 구르는 동안
다리 클립을 대기(Idle)로 바꿔 두었는데, 구르기가 끝나면 걷기가 **처음부터**
다시 시작합니다 - 그 0.15초 동안 몸은 아직 빠르게 나가는데 발은 이제 막 첫
걸음이라 미끄러졌습니다. 지금은 구르는 동안에도 걷기/달리기를 계속 돌립니다.
자세 층(`PoseOverride.ROLL`)이 다리를 덮고 있어 화면에는 안 보이고, 구르기가
풀리는 순간 이미 맞는 속도와 위상으로 돌고 있습니다.

#### 뒷걸음질

적이 가까우면 몸은 적을 봅니다(자동 조준). 그 상태로 물러나면 몸은 앞을 보는데
발은 뒤로 가야 하는데, 클립을 그대로 돌리면 **앞으로 걷는 다리로 뒤로
미끄러집니다** - 문워크입니다.

가는 쪽과 보는 쪽을 내적해서, 반대면 클립을 **거꾸로** 돌립니다. 문턱(±0.25)
사이에서는 직전 판단을 유지합니다 - 옆으로 걸을 때 0 근처에서 부호가 떨리면
다리가 앞뒤로 발작합니다.

![걷기와 뒷걸음질](out/screenshot_back.png)

*왼쪽이 걷기, 오른쪽이 뒷걸음질 클립. 같은 순간인데 보폭이 다릅니다.*

처음에는 걷기를 그대로 거꾸로 돌렸는데 **보폭이 앞걸음 그대로**라 발이 뒤로
성큼 뻗었습니다. 사람은 뒤로 갈 때 발을 멀리 내밀지 않습니다 - 발밑이 안
보이니 짧게 더듬습니다. 보폭만 줄인 사이클(다리 20도)을 따로 구워 그것을
거꾸로 돌립니다.

**뒤로 갈 때는 이동도 느립니다(0.6배).** 사람이 그렇기도 하고, 무엇보다 뒤로도
같은 속도로 도망칠 수 있으면 돌아설 이유가 없습니다 - 적에게 등을 보이는
위험을 감수할지가 선택이 되려면 값이 있어야 합니다.

거꾸로 돌리면 바닥을 미는 자가 조금 달라집니다("두 발 중 더 많이 민 쪽" 이라
부호를 뒤집으면 고르는 발이 달라집니다). 뒷걸음질 클립의 값을 따로 재서
맞췄습니다 - 실측 발/몸 = **1.03~1.05**.

적도 같습니다 - 원거리 적은 가까워지면 물러나고 근접 적도 재사용 대기 중에
물러납니다.

**`velocity` 가 아니라 실제로 움직인 속도**(`get_real_velocity`)를 씁니다.
`velocity` 는 "가려는" 속도라 벽에 붙어 밀고 있을 때도 그대로 남습니다 -
그걸로 다리를 돌리면 벽 앞에서 제자리 질주가 됩니다.

검사도 같은 자로 합니다(`--pose=skate`, 적은 `--pose=foeskate --foe=<종류>`).
발이 민 거리와 몸이 간 거리를 나란히 더해 비율을 찍습니다. 구르기를 섞어 돌린
결과 **0.95 ~ 1.05** 입니다.

#### 적의 보폭을 5배 작게 재고 있었습니다

적만 한참 미끄러지고 있었습니다(실측 발/몸 = 2.1~4.3). 원인은 클립이 아니라
**재는 자리**였습니다 - 보폭을 적의 **루트 노드 기준**으로 쟀는데, 적은 자기
노드를 돌리지 않고 몸통(`_pivot`)만 돌립니다. 옆으로 걸어갈 때 앞뒤 성분이
사라져 보폭이 5배 작게 나왔고, 그 작은 값으로 나누니 다리가 그만큼 빨리
돌았습니다.

주인공 쪽은 처음부터 `pivot` 기준이라 멀쩡했습니다. 같은 실수를 한쪽에서만
한 셈입니다.

| | 잘못 잰 값 | 몸통 기준 | 배속 |
|---|---|---|---|
| 적1_박치기 | 0.189 | **1.141** | 7.0 -> 1.5 |
| 적3_던지기 | 0.277 | **0.994** | 5.6 -> 1.6 |
| 선생님 | 0.618 | **1.304** | 2.3 -> 1.1 |

고친 뒤 발/몸이 **1.01~1.05** 입니다. 안전장치(클램프)도 9.5 에서 4.0 으로
내렸습니다 - 제대로 잰 값에서는 1.5 언저리라, 그보다 훨씬 큰 배속이 나오면
그건 또 무언가 틀렸다는 뜻입니다.

> 모델을 바꾸거나 클립을 다시 구우면 **이 값들도 다시 재야 합니다.** 보폭은
> 다리 길이와 흔드는 각도에서 나오므로 캐릭터마다 다릅니다.

### 시점 두 가지

옵션 판의 `시점` 으로 바꿉니다.

![어깨 너머](out/screenshot_shoulder.png)

| | 무엇이 다른가 |
|---|---|
| **위에서** (기본) | 63도로 내려다봅니다. 방 전체와 적의 배치가 한눈에 |
| **어깨 너머** | 아이 눈높이 뒤 3m. 덜 보이는 대신 같은 적이 훨씬 크고 가깝게 |

로그라이크가 위에서 보는 데는 이유가 있습니다 - 어디에 무엇이 있는지가
판단의 재료입니다. 어깨 너머는 그 재료를 덜 주는 대신 **덜 보이는 것이 곧
긴장**이 되는 쪽입니다. 어느 쪽이 맞다기보다 다른 게임이 됩니다.

**따로 시점 조작은 두지 않았습니다.** 폰에서는 엄지가 둘뿐이고 하나는 이동,
하나는 버튼에 가 있어서 시점을 맡길 손가락이 없습니다. 카메라가 몸을 따라
도니 **가는 쪽이 곧 보는 쪽**입니다.

바꾸면 따라오는 것이 셋 있습니다.

- **이동 입력이 카메라 기준이 됩니다.** 내려다볼 때는 위 키가 언제나 세계의
  같은 쪽이어도 됩니다(카메라가 안 도니까요). 어깨 너머에서 그대로 두면
  몸을 돌릴 때마다 같은 키가 다른 쪽으로 가서, 앞으로 가려다 옆으로 걷습니다.
- **마우스 조준을 끕니다.** 화면의 한 점을 가슴 높이 평면에 내려서 쓰는
  방식이라, 카메라가 거의 수평이면 광선이 평면과 나란해져 조금만 움직여도
  겨누는 점이 수십 미터씩 튑니다. 대신 가는 쪽과 가까운 적이 방향을 정합니다.
- **벽을 걷어내는 반경을 1.15m 에서 0.55m 로 줄입니다.** 카메라가 6m 밖이
  아니라 3m 뒤라, 같은 반경이면 벽 하나가 통째로 사라져 어디가 방인지
  안 보입니다.

카메라가 벽에 파묻히지 않게 뒤로 광선을 쏴서 앞으로 당겨 옵니다. 다만
**1.7m 아래로는 안 당깁니다** - 벽에 몰렸다고 0.8m 까지 붙이면 뒤통수가 화면
절반을 덮어, 파묻히는 것보다 오히려 안 보입니다. 광선은 카메라가 실제로 서는
자리(옆으로 0.42m 비켜선 곳)에서 쏩니다.

### 발밑 그림자

캐릭터가 바닥에 붙어 있는 것으로 보이게 하는 **가짜 그림자**를 깔았습니다.
해 그림자로는 안 됩니다 - 폰과 웹(Compatibility 렌더러)에서는 방향광의 그림자를
꺼 두었고(화면을 한 번 더 그리는 작업이라 폰에서 가장 비쌉니다), 켠다 해도 해가
비스듬해서 그림자가 발이 아니라 옆에 눕습니다.

가운데가 진하고 가장자리로 사라지는 원 하나입니다. 두 번 고쳐 잡았습니다.

- **곱하기 합성(MUL)을 쓰면 안 됩니다.** 알파가 0 인 자리도 색은 검정이라
  그대로 곱해져서, 부드러운 원이 아니라 **검은 사각형**이 깔립니다.
- **몸통보다 넓게** 깔아야 보입니다. 내려다보는 각도라 몸이 그림자를 거의 다
  가려서, 좁게 깔면(반지름 1.15배) 발끝에 자국만 남습니다. 1.9배로 넓혔습니다.

해도 조금 세웠습니다(-62 -> -70도). 데스크톱에서만 보이는 그림자이지만, 발밑
그림자와 방향이 어긋나면 둘이 따로 놉니다.

멈춥니다 - 끝없이 커지면 복도를 못 지납니다).

선생님만 예외입니다. 그쪽 크기는 모델 자체가 1.65m 라서 나오는 것이고,
어른이라는 정체성이라 줄이지 않습니다.

### 호흡 — 하나의 게이지를 나눠 씁니다

재사용 대기만 있을 때는 모든 기술을 늘 쓸 수 있어서, 무엇을 쓸지가 "지금 뭐가
준비됐나" 로만 정해졌습니다. **하나의 게이지**를 나눠 쓰면 무엇을 포기할지가
매번 생깁니다.

| | 호흡 |
|---|---|
| 가득 | **500** (시험 중. 설계값은 100) |
| 고함 | **80** |
| 구르기 | **60** |
| 잡기 / 밀치기 | **10** |
| 들고 있는 동안 | 0.1초에 0.5 (초당 5) |
| 차오르는 속도 | **초당 60**, 쓰고 나서 0.3초 뒤부터 |

값의 비율이 곧 설계입니다. 고함 한 번이면 숨이 거의 바닥나고(100 → 20),
가득 차기까지 1.3초가 걸립니다(30/초 -> **60/초** 로 두 배 올렸습니다. 뜸 0.3초는
그대로라 "바닥났다" 는 순간은 남고, 바닥에서 기다리는 시간만 줄었습니다). 대신 **고함에 맞은 적은 1초간 굳습니다** -
움직이지도, **방향을 바꾸지도** 못합니다.

그 1초가 이 판의 핵심입니다. 잡기는 등 뒤에서만 되는데 적은 늘 이쪽을 보고
돌기 때문에, 그냥 걸어서는 뒤를 잡을 수 없습니다(실측: 정면도가 0.88 에서 더
안 벌어짐). 굳어 있는 1초 동안은 돌지 않으므로 그때 돌아 들어갈 수 있습니다.
그래서 **"고함으로 굳히고 → 뒤로 돌아 잡고 → 던진다"** 가 한 줄로 이어지고,
그 값이 80 + 10 = 90 입니다. 한 호흡에 딱 한 번 할 수 있는 양입니다.

들고 있으면 계속 새는 것은 "집었으면 쓰라" 는 압력입니다. 오래 들고 있을수록
던지고 나서 남는 숨이 줄어듭니다.

HUD 의 파란 게이지가 호흡입니다(빨간 것은 투지)(예전에는 구르기 재사용 대기였습니다). 고함을
지를 수 없는 동안(80 미만)에는 색이 죽어서, 숫자를 읽지 않아도 지금 지를 수
있는지가 보입니다.

측정으로 확인했습니다 - 고함 100 → 20, 잡기 10.2, 들고 있을 때
5.0/초, 고함 경직 1.00초.

### 터치는 가장 가까운 버튼으로

버튼 안을 정확히 눌러야 하면, 화면을 보지 않고 누르는 엄지는 늘 조금씩
빗나갑니다. 그때마다 아무 일도 안 일어나면 게임이 먹통처럼 느껴집니다.

버튼은 **그림만** 맡고, 눌림 판정은 `touch_controls.gd` 가 직접 합니다 - 닿은
자리에서 **170px 안의 가장 가까운 버튼**을 누른 것으로 봅니다. 버튼끼리는
140px 넘게 떨어져 있어서 헷갈리지 않습니다.

자기 검사로 확인했습니다:

```
버튼 정중앙        -> 구르기
90px 옆으로 빗나감  -> 구르기   (예전에는 헛손질)
120px 위로 빗나감   -> E        (실제로 그쪽이 더 가까움)
300px 밖           -> 없음
```

고함과 구르기의 자리도 맞바꿨습니다. 엄지가 가장 편한 구석은 위험을 넘기는
쪽(구르기)이 차지하는 편이 낫습니다.

### 자세 층 — 클립 위에 덮어쓰기

`scripts/pose_override.gd`. 걷기·대기·밀기는 구운 클립이 있지만 구르기와
"잡고 있는 자세" 는 클립이 없습니다. 그렇다고 새로 구우면 구르는 동안 다리가
멈추고, 잡은 채로 걸을 수 없습니다. 그래서 클립은 그대로 두고 **특정 본만**
목표 자세로 당깁니다(`weight` 로 섞음).

| 자세 | 누구에게 | 무엇을 |
|---|---|---|
| `ROLL` | 주인공 | 고개·등·허벅지·팔을 한꺼번에 접어 ㄷ 자로 맙니다 |
| `CARRY` | 주인공 | 두 팔을 앞으로 모읍니다 |
| `HELD` | 잡힌 몹 | 머리와 다리를 앞으로 내밀어 몸을 굽히고, 팔을 좌우로 휘저어 발버둥칩니다 |

구르기에서 **접힌 모양이 회전보다 먼저 읽힙니다.** 크기만 줄여 돌리면 막대가
굴러가는 것으로 보입니다.

여기서 두 번 헤맸습니다.

- 재정의할 함수 이름이 `_process_modification` 이 아니라
  **`_process_modification_with_delta(delta)`** 입니다. 틀리면 오류 없이
  **한 번도 안 불립니다.**
- `Skeleton3D.get_bone_global_pose()` 는 자세 층이 손대기 **전**의 값을
  돌려줍니다. 그걸로 손 위치를 읽으면 팔을 앞으로 뻗어 놓고도 손은 몸 옆에
  있는 것으로 계산됩니다. `BoneAttachment3D` 로 읽어야 맞습니다.

### 구르기 — 회전을 이동에 매달았습니다

수치가 어긋나 있었습니다.

| | 전 | 후 |
|---|---|---|
| 한 바퀴에 걸리는 시간 | 0.40초 (`0.80 x ROLL_TIME` 로 못 박음) | **0.28초 = 이동 시간과 같음** |
| 회전축 높이 | 허리의 0.48배까지 **내려감** | 허리의 **1.5배까지 올라감** |

이동은 0.28초에 끝나는데 회전은 0.40초까지 이어져서, 마지막 0.12초 동안
**멈춘 채로 계속 돌았습니다.** 굴러가는 것이 아니라 제자리에서 도는 것으로
보이던 이유입니다. 한 바퀴가 끝나는 시점을 `DASH_TIME / ROLL_TIME` 비율로
적어 두었으므로, 구르기 속도나 거리를 바꾸면 회전이 저절로 따라옵니다.

회전축은 방향이 반대였습니다. 바닥을 스치는 그림을 노리고 축을 **내렸는데**,
축이 발치에 붙으니 구르는 것이 아니라 바닥에 누워 비비는 것처럼 보였습니다.
축이 올라가야 몸이 바닥에서 떠서 넘어가는 것으로 읽힙니다.

측정으로 확인했습니다(`--pose=roll --trace-at=1`):

```
 t=0.03  회전 -30도   축높이 0.60   머리높이 0.91  진행방향 +0.16
 t=0.10  회전 -88도   축높이 0.70   머리높이 0.72  진행방향 +0.31
 t=0.17  회전 -143도  축높이 0.77   머리높이 0.55  진행방향 +0.18
 t=0.23  회전 -195도  축높이 0.82   머리높이 0.56  진행방향 -0.06
```

한 가지는 물리적으로 맞출 수 없습니다. 바퀴처럼 미끄러지지 않고 구르려면 한
바퀴에 `2πr` 만큼 가야 하는데, 축 높이 0.7m 면 4.4m 입니다. 실제 구르기 거리는
1.4m 라 **몸은 땅보다 3배 빨리 돕니다.** 거리를 3배로 늘리거나 한 바퀴를 3분의
1로 줄이면 맞지만, 둘 다 회피 기술로서는 못 쓸 값입니다.

### 소리

`scripts/sfx.gd`. 지금은 고함 하나뿐입니다 - `assets/audio/shout_a1.wav`,
**vtos 프로젝트**(`C:\_projecttos`)의 라이브러리에서 `a1` 이라는 이름으로
잘라 둔 클립입니다(1.05초, 모노 44.1kHz).

3D 소리가 아닙니다. 카메라가 늘 주인공을 따라다녀서 주인공이 내는 소리는
언제나 화면 한가운데에서 나므로, 거리 감쇠와 방향을 계산해 봐야 결과가
같습니다. 적이 내는 소리를 넣을 때 3D 로 나누면 됩니다.

재생기를 네 개 두고 노는 것을 골라 씁니다. 하나면 앞 소리가 끊깁니다. 그리고
**음높이를 매번 ±6% 흔듭니다** - 같은 파일이 그대로 반복되면 세 번째부터
기계음으로 들립니다.

새 소리를 넣으려면 `Sfx` 에 상수를 하나 더하고 `Sfx.play()` 를 부르면 됩니다.
파일이 없으면 조용히 넘어갑니다 - 소리가 없다고 게임이 멈출 이유는 없습니다.

#### 배경음

`assets/audio/bgm1.ogg` - 역시 vtos 의 `bgm1` 클립입니다(3.2초 스테레오 루프).
제목 화면부터 끝까지 **한 번만** 겁니다. 층이 바뀔 때마다 다시 걸면 이어지지
않고 끊깁니다.

재생기를 효과음과 나눠 두었습니다. 같은 재생기를 나눠 쓰면 고함이 배경음을
끊거나 그 반대가 됩니다. 크기는 -14dB 로 효과음보다 확실히 낮췄습니다 - 같은
크기로 깔면 무엇이 신호이고 무엇이 분위기인지 구분되지 않습니다.

3.2초짜리 조각이라 반복이 필수인데, 원본에 반복 표시가 있어도 들여올 때 꺼질
수 있어서 코드에서 못 박습니다. 확인했습니다 - 재생 위치가 3.04초에서 0.84초로
되감기며 계속 돕니다.

배경음은 **스트림**이라 엔진 믹서를 거칩니다. 고함(WAV)이 웹에서 믹서를
건너뛰는 것과 다른 길이라, 옵션의 `소리` 줄에서 `엔진` 값이 살아 있는지로
믹서가 도는지도 같이 볼 수 있게 됐습니다.

#### 폰에서 소리가 안 들리던 것 - 결말

**아이폰의 벨소리 무음 모드였습니다.** 웹 오디오는 영상과 달리 무음 스위치를
그대로 따르므로, 스위치가 켜져 있으면 신호가 정상으로 나가도 하나도 들리지
않습니다.

여기까지 오는 데 오래 걸렸고, 그 대부분은 **제가 잘못된 계측기를 믿었기**
때문입니다. 남겨 둘 만한 교훈이 셋 있습니다.

**엔진 버스 계측기는 웹에서 의미가 없습니다.** `default_playback_type.web` 의
힌트가 `Stream,Sample` 이고 값이 1 이므로 웹은 Sample 재생입니다 - WAV 가 엔진
믹서를 건너뛰고 브라우저로 바로 나갑니다. 그러니 소리가 잘 나고 있어도 버스
피크는 늘 조용합니다. 그것을 "안 나감" 이라고 표시한 탓에 멀쩡한 것을 고장으로
읽었습니다. 게다가 그 값을 처음 볼 때 `AudioServer.PLAYBACK_TYPE_*`(0=Default,
1=Stream, 2=Sample)에 대입해 **1=Stream 이라고 반대로 읽기까지** 했습니다.
숫자만 보지 말고 힌트를 읽었어야 합니다.

**껍데기가 캐시되고 있었습니다.** 서버가 모든 파일에 `max-age=600` 을 보내서,
wasm 과 pck 는 새로 받으면서 `index.html` 만 캐시에 남았습니다. 진단 코드와
오디오 훅이 전부 그 안에 있었으니, 고친 것들이 폰에 도달하지 않고 있었습니다.
지금은 html/js 만 `no-cache, must-revalidate` 입니다(ETag 로 재검증은 쌉니다).

**무음 스위치 우회는 오히려 소리를 죽였습니다.** 조용한 `<audio>` 를 틀어
오디오 세션을 바꾸는 널리 쓰이는 방법을 넣었더니, 브라우저 쪽 출력이
0.15 에서 **0.00** 으로 떨어졌습니다. 아이폰에서 HTMLMediaElement 와 WebAudio 가
섞이면 한쪽이 죽는 경우가 있고 여기서 그 일이 났습니다. 걷어냈습니다.

남긴 것은 둘입니다. 내보낸 HTML 머리의 훅이 `AudioContext` 를 붙잡아 **첫
터치에 깨우고**, 웹에서는 오디오 샘플레이트를 강제하지 않습니다
(`driver/mix_rate.web=0` - 아이폰은 대개 48000 인데 44100 을 강제하는 것은
그 자체로 옳지 않습니다). 진단 표시는 역할이 끝나 걷어냈습니다.

### 몹을 잡는 규칙

![등 뒤에서 잡기](out/screenshot_carry.png)

**등 뒤에서만 잡힙니다**(뒤쪽 110도). 앞에서 누르면 밀기가 나갑니다. 잡기가
더 센 기술이라 아무 데서나 되면 밀기를 쓸 이유가 없어집니다 - 뒤로 돌아
들어가는 수고가 그 값입니다.

잡고 있는 동안에는 **걷기만 됩니다.** 이동은 0.42배(달리기 문턱 아래라 걷기
동작만 나옵니다), 구르기와 고함은 막힙니다. 또래를 끌면서 뛸 수는 없고, 두
손이 이미 차 있습니다.

잡힌 몹은 **자리가 그대로**입니다. 들어 올리지 않고 두 손이 등을 잡아 앞으로
끌고 갑니다. 붙는 자리는 손 앵커에서 뽑으므로 자세가 바뀌어도 손과 몹 사이가
벌어지지 않습니다.

### 잡기가 안 잡히던 것

세 가지가 겹쳐 있었습니다.

- **중심끼리 거리를 쟀습니다.** 큰 상자는 눈앞에 닿아 있어도 중심이 멀어 사거리
  밖으로 계산됐습니다. 이제 몸집을 빼고 **표면까지의 거리**로 잽니다.
- **각도가 좁았습니다**(100도). 조준이 조금만 틀어지면 헛손질이 됐습니다.
  160도로 넓혔습니다 - 잡기는 겨냥하는 기술이 아니라 닿는 기술입니다.
- **대기 중에 누른 입력을 버렸습니다.** 0.25초까지 기억해 뒀다가 풀리는 순간
  씁니다. 버리면 "분명히 눌렀는데 아무 일도 안 일어났다" 가 됩니다.

잡은 뒤 대기도 0.33초에서 0.14초로 줄였습니다. 봇으로 같은 3000프레임을 돌려
비교하니 예전 값은 소품 잡기 0회, 고친 뒤에는 잡힙니다.

**가구도 이제 잡힙니다.** 예전에는 아예 안 잡히고 밀기로 넘어갔는데, 화면에서는
인형이든 상자든 그냥 "바닥의 물건" 이라 눌렀는데 안 잡히는 것으로만 느껴졌습니다.
규칙이 보이지 않으면 규칙이 아니라 고장입니다. 대신 **드는 값**을 비싸게
매겼습니다 - 걷는 속도 0.28배(몹을 끌 때보다도 느립니다), 숨은 초당 15씩. 숨이
바닥나면 손에서 놓칩니다.

## 원화 여덟 장에서 가구를 굽는데, 이름표가 두 번 어긋났습니다

`art_src/source/` 에 4면도(정면·우측면·좌측면·후면) 여덟 장을 받아 test3 로
구웠습니다. 그림에서 3D 까지는 test3 가 다 하므로, 이쪽이 한 일은 **어느 칸이
어느 면인지 정하는 것**과 게임에서 무엇으로 쓸지 고르는 것뿐입니다.

test3 의 시트 분할기는 칸을 왼쪽부터 찾아낸 뒤, 각 칸이 정면인지 측면인지를
실루엣 비율과 얼굴 검출로 **추측**합니다. 사람에게는 잘 맞는데 가구에는 얼굴이
없습니다.

```
붕붕카   1.우측면  2.정면  3.후면  4.좌측면   판정 11/100
                (실제로는 1.정면 2.우측면 3.좌측면 4.후면)
```

여덟 장이 전부 같은 판형이니 추측을 쓸 이유가 없었습니다. 보고서에 칸이
왼쪽부터 번호로 적히므로, 그 **번호를 정답 순서에 그대로** 대응시킵니다.
전처리(배경 제거·스케일 정렬)는 test3 것을 그대로 쓰고 바꾸는 것은 이름표뿐이라,
분할기가 나아지면 그 이득은 그대로 따라옵니다.

그런데 이름표가 한 번 더 어긋났습니다. **놀이매트는 옆모습이 없습니다** —
윗면과 아랫면 둘뿐인데, 기본 순서(정면·우측면)로 읽는 바람에 아랫면을 옆모습
자리에 넘겼습니다. 생성기는 그 "옆모습" 이 매트만큼 넓으니 두께도 그만큼이라고
읽었습니다.

```
아랫면을 옆모습으로:  1.15 × 1.50 × 0.84   ← 베개
정면·후면으로:        1.15 × 1.50 × 0.06   ← 매트
```

두께를 눌러 고치는 코드를 먼저 썼다가 지웠습니다. 눌러도 화면에서는 매트로
보였을 테지만, 그건 **틀린 입력을 그대로 두고 결과만 손보는 것**입니다. 판형이
다르면 판형을 적어 주는 것이 맞습니다(도구의 `order`).

미끄럼틀도 판형이 달라(측면이 위아래 두 벌) 자동 분할이 여섯 칸을 찾습니다.
쓸 넷을 자리로 집어 줍니다.

## 앞면이 어느 축인지, 채도로는 못 갈랐습니다

책장 때는 텍스처 채도로 앞뒤를 갈랐습니다 — 앞면에만 책 색이 있어서 +Z 쪽
정점의 12%가 나무색이 아니고 -Z 쪽은 0% 였습니다. 같은 방법을 새 소품 여덟에
그대로 썼더니 이렇게 나왔습니다.

```
장롱      +Z 83.4  |  -Z 82.2
정리대    +Z 71.5  |  -Z 74.3
옷장      +Z 110.1 |  -Z 112.6
```

**사면이 다 알록달록해서 차이가 1% 안쪽입니다.** 어느 쪽이 크든 우연입니다.

그래서 재는 대상을 바꿨습니다. 카메라는 사람을 따라 돌지 않고 늘 -Z 쪽을
봅니다(찍어서 확인: 보는 쪽 `(0, -0.89, -0.45)`). 그러니 소품을 각도 0 으로
세워 두면 **화면에 오는 것이 언제나 +Z 면**이고, 그 면에 장롱 문짝과 손잡이가
보이면 앞면이 +Z 입니다. 눈으로 보되 **보는 축을 고정해서** 봤습니다.

여덟 개가 전부 +Z 였습니다 — test3 를 `--convention unity` 로 돌린 결과라
책장·액자·시계와 같은 규약이고, 벽에 세우는 각도 계산이 그대로 맞습니다.

## 못 움직이는 것과 못 지나가는 것은 다른 이야기입니다

가구는 `fixed`(붙박이), 장난감은 `heavy`(밀리는 것)로 갈랐습니다. 그런데
카페트와 놀이매트를 붙박이로 두니 **방 한가운데 보이지 않는 벽**이 생겼습니다.
눈에는 바닥인데 발이 걸리는 물건은 규칙이 아니라 고장으로 보입니다.

가구를 `heavy` 로 낮추는 것은 답이 아닙니다 — 그러면 카페트가 밀려다닙니다.
필요한 것은 "못 움직인다" 와 "막는다" 를 **가르는 것**이었고, 이미 벽에 걸린
액자가 같은 처지였습니다(못 움직이고, 손이 안 닿는 높이라 안 막습니다).
그 처리를 `flat` 이라는 이름으로 꺼내 썼습니다.

실측(사람이 계속 밀어붙인 뒤):

| | 밀린 거리 | 사람과 거리 |
|---|---|---|
| 장롱 · 미끄럼틀 | 0.000m | 0.61 / 1.41 에서 **막힘** |
| 카페트 · 놀이매트 | 0.000m | 0.11 까지 붙었다 1.35 로 **지나감** |
| 장난감함 · 붕붕카 | 1.54 / 1.90m | **밀려남** |

## 가구가 아이를 가렸습니다

벽에 붙는 것만 비치게 해 뒀는데, 미끄럼틀은 방 한가운데 서고 높이가 1.84m 라
아이(1.25m)를 통째로 가립니다. 기준이 "벽에 붙었느냐" 가 아니라 **"가리느냐"**
라야 맞습니다 — 키가 1m 를 넘는 붙박이는 벽에 안 붙어도 비칩니다.

벽 자리도 손봤습니다. 벽 가구가 책장 셋에서 여섯으로 늘면서 겹쳐 서는 것이
눈에 띄기 시작해서, 이번 층에 쓴 칸과 **양옆 한 칸씩**을 피하게 했습니다.
가구는 한 칸(1.5m)보다 넓은 것이 많아 붙은 칸에 나란히 세우면 서로 파고듭니다.

## 크기는 캐릭터에 쓴 수를 그대로 씁니다

실물 크기로 구웠더니(장롱 1.8m, 옷장 1.2m) 아이 옆에서 한 치수 작아 보였습니다.
이 게임의 아이가 실물 0.85m 를 1.25m 로 키운 것이라서입니다 — 같은 이유이니
**같은 수(1.47)**를 씁니다. 장롱이 2.65m 로 서지만 벽 높이(2.8m) 안입니다.

## 필살기 — 나중에 동작을 더할 자리를 먼저 정했습니다

"추후 파생 동작을 만들 예정" 이라고 하셔서, 만드는 순서를 뒤집었습니다.
동작 셋을 먼저 짜고 나중에 정리하는 대신, **동작을 더하는 자리**를 먼저
정하고 그 자리에 셋을 넣었습니다.

`scripts/ultimate.gd` 하나가 게이지·발동 명령·시간 제한·동작 표를 다 가집니다.
`player.gd` 는 **몸을 움직이는 일만** 합니다. 동작 하나를 더하는 일은 이렇게
됩니다.

```gdscript
# ultimate.gd — 표에 줄 하나
"drink": {"cost": 20.0, "name": "숨 고르기", "keep": true},

# player.gd — 갈래 하나
"drink": _ult_drink()
```

게이지·명령·해제 규칙은 손댈 일이 없습니다. `keep` 을 false 로 두면 그 동작이
**마무리 기술**이 되어 쓰고 나서 모드가 끝나는데, 지금은 쓰는 데가 없지만
자리는 열어 뒀습니다.

판단과 연출을 나눈 이유가 이것입니다 — 섞어 두면 동작을 더할 때마다 두 곳이
함께 자라고, 그러면 규칙이 어디 있는지 아무도 모르게 됩니다.

**용기를 숨과 따로 둔 이유**: 숨은 쓰면 줄고 쉬면 차는 평상시의 밑천이고,
용기는 잘 싸울수록만 차는 상입니다. 하나로 합치면 필살기가 "오래 쉬면 나오는
것" 이 되어, 몰아치는 것과 이어지지 않습니다.

**맞아도 게이지는 안 깎습니다**(연속만 끊깁니다). 깎으면 한 대 맞을 때마다
여태 쌓은 것이 사라지고, 그러면 필살기가 "안 맞는 사람만 쓰는 것" 이 되어
정작 몰릴 때 못 씁니다.

**세상을 멈추는 방법**은 `get_tree().paused` 가 아닙니다 — 그러면 주인공까지
멈춥니다. 멈춰야 하는 것은 주인공 말고 전부라, 멈추는 쪽(적·날아가는 것·가시)이
`Game.world_frozen` 을 스스로 보게 뒀습니다. 고르기 화면이 `phase` 를 보는
것과 같은 방식입니다.

**연달아 구르면 다음 적으로 갑니다.** 한 번 들른 적은 건너뜁니다 - 안 그러면
붙어 있는 그 적에게 계속 다시 붙어서, 연타가 제자리걸음이 됩니다. 다 들렀으면
한 바퀴 다시 돕니다(거기서 끝내면 적이 적게 남았을 때 필살기가 도중에
끊깁니다).

**포효의 호랑이는 발밑에 깝니다.** 아이 높이에 띄우면 아이를 덮는데, 포효는
아이를 가운데 둔 원이라 그 원이 바닥에 그려지는 편이 범위와도 맞습니다.

**명령은 음이 올라갑니다**(1.0 → 1.26 → 1.5). 폰에서는 버튼을 훑는 동안
손가락이 화면을 가려서, 어디까지 갔는지 눈으로는 잘 안 보입니다.

필살 모드에서는 **사람 말고 다 감춥니다.** 던전도 소품도 함정도 사라지고
배경이 검정이 되어, 주인공과 적과 그 사이의 이펙트만 남습니다. 되돌릴 때는
감춰 둔 목록만 되돌립니다 - "전부 다시 보이게" 로 풀면 주운 소품이나 죽은
적까지 되살아납니다.

주변광은 0 으로 안 내렸습니다. 완전히 끄면 해가 안 닿는 면이 새까매져 아이가
실루엣만 남는데, 그러면 누가 누구인지 알아볼 수 없습니다.

한 바퀴를 재서 확인했습니다(`--pose=ult`).

```
게이지 1.00 → 달려들기 0.82 (가장 가까운 적까지 0.50m)
            → 밀어붙이기 0.70
            → 포효 0.36,  그 한 번에 적 아홉의 체력합 342 → 150
손 놓고 1.85초 뒤: 모드 해제, 세상 다시 흐름
```

폰에서는 버튼 위를 손가락 하나로 훑으면 명령이 들어갑니다. 훑고 지나가는
것도 누름으로 보게 고쳤습니다 — 세 번을 따로 탁탁탁 누르는 것보다 빠르고,
명령이 **한 동작**으로 느껴집니다.

## 밀어도 안 죽는 적 — 타이머 하나가 멈춰 있었습니다

재현부터 했습니다. 체력을 1 로 깎고 계속 밀었더니:

```
f=120  체력=-67   죽음=false  밀림=0.2833  보류=true
f=180  체력=-101  죽음=false  밀림=0.2833  보류=true
```

체력이 **-101** 인데 안 죽고, `밀림`(밀려나는 남은 시간)이 **0.2833 에서
얼어붙어** 있습니다.

`_die` 에는 "밀려나는 중이면 멈춘 뒤에 쓰러진다" 는 규칙이 있습니다(밀어서
죽인 적이 제자리에서 증발하지 않도록 넣은 것입니다). 그런데 그 `밀림` 을
줄이는 코드가 `_settle` **안에만** 있었고, `_settle` 은 적이 깨어 있지 않거나
휘청이는 동안에만 불립니다.

밀기는 밀림 0.45초와 휘청임 0.45초를 같이 겁니다. 휘청임은 매 프레임 줄지만
밀림은 `_settle` 안에서만 주는데, **휘청임이 한 프레임 먼저 0 이 되는 순간**
그 프레임부터 `_settle` 이 안 불립니다. 밀림은 거기서 멈추고, 다시는 안
줄어듭니다.

**고함으로만 죽던 이유도 같습니다.** 고함은 휘청임을 1초 겁니다 - 그 1초
동안 `_settle` 이 돌면서 멈춰 있던 밀림을 마저 빼 줍니다.

밀림을 **어느 갈래로 가든 지나가는 자리**로 옮겼습니다(`_tick_knock`). 고친
뒤에는 f=90 에 미끄러진 뒤 쓰러집니다. 미룸에 **시간 제한(1.2초)** 도 뒀습니다 -
죽음은 미룰 수는 있어도 취소될 수는 없는 일이라, 조건이 무슨 이유로든 안
풀려도 결국 죽어야 합니다.

## 부딪히면 더 아픕니다

밀리거나 던져진 몸이 벽이나 다른 적에 **정면으로** 부딪히면 피해가 더
들어갑니다. 피해를 따로 정하지 않고 **부딪힌 속도**에서 뽑으므로, 「밀치는
힘」이 그대로 반영되고 벽을 등진 적을 미는 것이 자리 선택이 됩니다.

만들면서 두 번 걸렸습니다.

**속도를 늦게 재고 있었습니다.** `move_and_slide` 는 벽에 닿는 순간 그 방향
속도를 이미 지웁니다 - 7.13m/s 로 박았는데 판정 뒤에 재니 0 이라, 아무리 세게
밀어도 부딪힌 것이 되지 않았습니다. **부딪히기 직전** 값을 적어 두고 씁니다.

**적끼리는 서로 통과합니다.** `collision_mask` 에 적이 없어서(겹침은 서로
벌리는 규칙으로 풉니다) 미끄러짐 충돌로는 영영 안 잡힙니다. 적은 거리로,
벽은 충돌로 봅니다.

속도에 상한(9m/s)을 뒀습니다. 물리가 겹친 몸을 밀어낼 때 한 프레임 10~25m/s
가 찍히는데(실측), 그대로 곱하면 벽에 낀 적이 한 방에 죽습니다 - 세게 민 것이
아니라 물리가 튄 것이라 게임에서 벌어진 일과 무관합니다.

## 맵이 대부분 복도였습니다

"긴 복도가 나와서 흐름이 느리다" 를 숫자로 옮겼습니다.

```
전:  방 비율 60~79%   복도 130~493칸   가장 긴 곧은 복도 27~52m
후:  방 비율 86~90%   복도  44~104칸   가장 긴 곧은 복도  9~24m
```

27m 복도는 걸어서 **9초**, 52m 면 17초입니다. 그동안 아무 일도 없습니다.

가장 큰 원인은 **잇는 순서**였습니다. 시작 방에서 **먼 순서로 정렬**해 그
차례대로 이었는데, 그러면 길이 판을 갈지자로 가로지르면서 이어야 할 두 방이
매번 판의 반대편에 놓입니다. 가장 가까운 방부터 잇게 바꾸니 복도 하나하나가
짧아졌고, 차례의 끝에 남는 방은 여전히 시작에서 먼 방이라 출구 자리로 그대로
씁니다.

여기에 판을 좁히고(48~64 → 34~44) 방을 더 크게 놓았습니다. 적 수는 방 수가
아니라 층에서 나오므로(`4 + 층×2`) **어려움은 그대로**이고, 걷는 시간이 줄어든
만큼 마주치는 시간이 늘어납니다.

## 편집 사고를 하나 냈습니다

부딪힘 판정을 넣다가 한 줄을 잘못 고쳐, `_charge_contact`(적1_박치기의 박치기가
주인공에 닿았는지 보는 자리)의 계산식을 **덮어썼습니다.** 배포된 pck 는 스크립트를
바이너리로 담고 있어 원문을 되찾지 못했습니다.

같은 뜻으로 다시 썼습니다 - **내 몸 반지름 + 주인공 몸 반지름 + 손끝 여유
0.12m**. 주인공의 달려들기(`_drive_lunge`)와 같은 방식이라 어느 쪽 몸집이
커져도 둘이 같이 따라갑니다. 원래 값이 이것과 달랐다면 박치기가 닿는 거리가
조금 달라졌을 수 있습니다.

## 폰이 뜨거워지는 것 — 프레임을 60에서 멈췄습니다

"할수록 발열이 심해진다" 는 말이 앞의 렉과 한 이야기였습니다. **아무것도 안
걸어 두고 있었습니다** — 기기가 낼 수 있는 만큼 그립니다. 120Hz 화면이면 두
배를 그리고, 그 몫이 그대로 열이 됩니다. 뜨거워지면 기기가 스스로 성능을
낮추므로 **오래 할수록 느려집니다.** "쌓이는 것이 없는데 나중에 느려진다" 가
그것으로 설명됩니다.

웹·모바일에서 `Engine.max_fps = 60` 입니다. 물리도 60Hz 라 그 위로 그려서
얻는 것이 없습니다.

이것으로 충분한지는 폰에서 봐야 합니다. 남은 큰 몫이던 **텍스처 262MB** 는
아래 「폰 규격」 에서 41MB 로 줄였습니다.

## 소용돌이를 부채꼴에서 뽑았습니다

원뿔로는 **부채꼴을 못 덮습니다.** 판정은 각도 30~132°짜리 부채꼴인데 원뿔의
밑면은 언제나 온전한 원이라, 옆으로는 판정 밖까지 삐져나오고 앞으로는
모자랍니다.

그래서 메시를 부채꼴에서 그대로 뽑았습니다 — 꼭짓점이 입이고 테두리가 바닥의
호입니다. 위에서 보면 칠해 둔 부채꼴과 정확히 겹칩니다.

```
판정 2.18m / 50도   ->  판 2.18m / 50도
판정 4.79m / 105도  ->  판 4.79m / 105도
```

**그러면 어떻게 도는가**: 메시를 돌리면 부채꼴 밖으로 나갑니다. 도는 것은
**무늬만** 합니다(UV 가 이미 극좌표입니다) — 형태는 판정에 붙들려 있고 움직임만
도는 셈입니다. 각도는 셰이더가 잘라 쓰므로(`arc_frac`) 모으는 동안 매 프레임
메시를 새로 만드는 값도 안 듭니다.

**모으기 시작하는 순간부터 뜹니다.** 소리는 누르는 순간부터 나고 부채꼴도
그때부터 자라는데 소용돌이만 마지막에 나오면, 셋이 서로 다른 것을 말합니다.

## 록온을 밀기 사거리에 맸습니다

3.9m 로 박혀 있었습니다. 그때는 고함 사거리(2.7)보다 조금 넓게 잡은 것이었는데,
고함이 **모은 만큼 1.29~5.7m** 로 변하게 되면서 어느 값과도 안 맞게 됐습니다 —
고함을 판 사람은 겨눌 수 있는 적에게 록온이 안 걸렸습니다.

```
록온 = 밀기 사거리 + 1.2m
       2.60 + 1.2 = 3.80m       「긴 팔」을 찍으면 5.00m
```

록온이 실제로 필요한 순간은 **붙어서 미는 순간**입니다. 고함은 부채꼴이 넓어서
대충 그쪽만 보면 맞지만, 밀기는 한 사람을 정확히 겨눠야 하고 등 뒤냐 앞이냐까지
갈립니다.

**기본도 켬으로 되돌렸습니다.** 껐던 이유는 "겨누는 일이 사라진다" 였는데,
범위를 붙는 거리로 좁히니 그 걱정이 줄었습니다.

**「긴 팔」은 걷어냈습니다.** 밀기 계통에 있던 스킬인데, 스킬을 여섯으로 줄일
때 이미 빠졌고 값만 죽은 채 남아 있었습니다 — 더해도 아무 일이 안 일어나는
항이 식에 남아 있으면 다음에 읽는 사람이 "찍으면 늘어나는구나" 로 잘못 압니다.

사거리를 늘리는 것 자체가 별로였습니다: 달려드는 거리가 길어지면 더 멀리서
밀 수 있는 대신 **달려가는 동안 무방비인 시간**이 같이 길어져서 이득이 거의
없습니다.

## 고함 모으는 시간을 0.60초로

목소리가 살아 있는 길이(0.86초)에 맞춰 뒀던 것을 줄였습니다. 귀와 눈이 같은
것을 말한다는 점은 좋았지만 **손으로 쥐고 있기에는 길었습니다** — 최대로
지르려면 매번 거의 1초를 서 있어야 하고, 그동안 발이 0.2배로 묶입니다.

**소리는 그대로 끝까지 냅니다.** 다 모여 저절로 나갈 때 목소리를 끊지 않으므로
남은 0.45초가 지르고 난 여운이 됩니다 — 끊으면 최대로 질렀는데 소리가 제일
짧아지는, 거꾸로 된 일이 생깁니다. 살짝 눌렀다 뗄 때만 거기서 끊깁니다.

## 고함에 소용돌이

파란 구슬을 걷어내고 **원뿔 셋을 겹친 소용돌이**를 세웁니다. 구슬은
"퍼졌다" 는 됐지만 소리가 밀어낸다는 그림이 아니었고, 모은 만큼 커지는 것과도
안 붙었습니다.

형태만으로는 겹친 고깔입니다. 빨려드는 느낌의 8할은 **표면 무늬가 도는
것**에서 나옵니다 — UV 를 극좌표로 바꿔 각도로 돌리고 반지름으로 안쪽으로
흘리면 같은 노이즈가 나선으로 감깁니다. 안쪽 원뿔일수록 빨리 돌려(0.9 →
0.42초) 층 사이가 엇갈리게 했고, 정점도 살짝 흔들어 테두리가 울렁이게 했습니다.

**과하지 않게 잡았습니다.** 수채화 배경에 카툰 외곽선인 그림체라 화면을 채우는
이펙트는 싸웁니다. 넷 이상 겹쳐 보니 더하기로 섞이는 터라 겹칠수록 밝아져 파란
덩어리가 됐습니다 — 셋에 알파 0.34, 0.42초입니다.

### 처음에는 방향이 없었습니다

바닥에 세운 깔때기로 만들었습니다. 소용돌이로는 보였지만 **누가 만든 것인지**
안 읽혔습니다 — 발 앞에 물기둥이 하나 솟은 것에 가까웠고, 지르는 방향과도
상관이 없었습니다. **꼭짓점을 입에 두고 앞으로 벌리니** 소리가 나가는 길이
그대로 그림이 됩니다.

벌어지는 각은 부채꼴(최대 132°)에 안 맞춥니다. 그대로 따르면 원뿔이 아니라
원반이 됩니다 — 범위를 가르치는 일은 바닥에 칠한 부채꼴이 이미 하고 있으므로,
이쪽은 "소리가 나간다" 만 말하면 됩니다.

### 재 보니 5.2ms 였습니다

고함마다 원뿔과 재질을 새로 만들고 있었습니다. **프레임의 3분의 1**입니다.
셋이 다른 것은 크기·빠르기·진하기뿐이라 세 벌만 만들어 두고 홀더의 `scale` 로
크기와 세기를 내게 했습니다. 고친 뒤에는 잡음에 묻힙니다.

재는 김에 부채꼴과 먼지도 하나씩 빼 봤는데 값이 7~9ms 사이에서 그대로
흔들렸습니다 — **그건 재는 값 자체의 잡음**이고, 실제로 무거웠던 것은 소용돌이
하나였습니다.

## 자동차 — 떼는 쓸 수 있게, 대신 한 번만

조작을 아예 안 먹게 뒀더니 타는 순간부터 3.4초가 **화면을 구경하는 시간**이
됐습니다. 밀고 있으면 꺾는 기준이 그쪽으로 바뀌게 했습니다.

처음에 끌어당기는 힘만 올렸는데(1.1) **아무 소용이 없었습니다** — 0.62초마다
±2 라디안씩 제멋대로 꺾는 힘이 훨씬 세서, 밀고 있는 쪽의 반대로 가는 일이
잦았습니다. 끌어당기는 힘을 3.5 로 올리고 **꺾는 기준 자체를 입력 쪽으로**
바꿔야 했습니다. 실측: +x 로 밀면 가는 쪽 x = +0.94.

**한 번 타면 끝입니다.** 다시 탈 수 있으면 방 하나가 무한한 무적 시간이
됩니다 — 내렸다 다시 타면 되니까요. 다 쓴 차는 앞머리를 기울이고 연기를 뿜고,
그 앞에서 밀기를 누르면 밀기가 그대로 나갑니다.

**곁다리로 구멍을 하나 막았습니다** — 물장난 중에도 탈 수 있었는데, 물장난
갈래가 먼저라 자동차 시계가 멈춘 채로 남았습니다(2.23초에 0.75초만 줄었습니다).

## 고함은 다 모이면 저절로 나갑니다

소리가 끝난 뒤에도 누르고 있으면 부채꼴이 계속 떠 있었습니다. 그 뒤로는 눌러
봐야 아무것도 안 늘어나는데 **"아직 모으는 중" 이라는 거짓말**을 하는 셈이고,
소리는 이미 끝나 귀와도 어긋납니다. 다 모이는 순간 그대로 나갑니다.

## 물물교환하는 아이 — 물 안에서 테두리 위로

서서 기다리는 상인이 아니라 **놀고 있는 또래**입니다. 처음에는 물 안에
기대앉히려 했는데, 자세가 아무리 해도 안 나왔습니다. **재 보니 이유가
있었습니다.**

```
풀장 테두리 높이 1.20m     아이 키 1.25m
```

거의 같습니다. 물 안에 앉으면 무엇을 해도 테두리에 가립니다. **테두리 위에
걸터앉는** 쪽으로 바꾸니 온몸이 보이고 다리도 물 쪽으로 늘어뜨릴 수 있습니다.

팔은 아래로 내려 테두리를 짚고, 다리는 조금 벌려 무릎을 굽히고, **그 무릎을
걷듯이 폈다 굽힙니다**(−78° ± 22°). 두 다리가 반 바퀴 어긋나 있어서 하나가
펴질 때 다른 하나가 굽습니다 — 같이 움직이면 걷는 것이 아니라 뛰는 것이 되고,
앉아서 뛰면 발버둥으로 보입니다.

자리는 **화면에서 먼 쪽**(−Z)이고 몸통을 180° 돌려 **얼굴이 화면을 봅니다.**
몸통은 안 돌립니다 — 팔을 짚은 자세라 좌우로 흔들리면 짚은 팔이 테두리를
드나듭니다. 고개만 아주 조금: 두리번거리면 기다리는 것이 아니라 무언가를 찾는
것으로 보입니다.

**깔개와 조명을 걷어냈습니다.** 깔개는 "이 방이 다르다" 는 신호였는데 풀장이
그 일을 대신하게 됐고, 물 위의 주황색 원반은 표시가 아니라 얼룩입니다.

둘이 같은 물에 있으므로 **말이 닿는 거리를 3.2 → 1.7m 로 좁혔습니다** — 넓게
두면 물가에 서기만 해도 교환 창이 열려서 물에 들어갈 방법이 없어집니다.

## 풀장에 물이 생겼습니다

반투명 파란 원판 하나였습니다. "물이 들었다" 는 됐지만 **가만히 있는
색면**이라, 화면이 멈추면 그냥 칠해 놓은 바닥이었습니다 — 물은 색이 아니라
움직임으로 알아봅니다.

방향이 다른 물결 셋을 겹칩니다. 하나면 줄무늬가 흐르는 것으로 보이고 둘이면
격자가 보입니다. 골은 짙게 마루는 옅게 칠해 깊이가 다른 것처럼 만들고, 마루
끝에만 하얗게 얹어 반짝이게 했습니다.

**정점은 안 흔듭니다.** 63도로 내려다보는 카메라에서는 수면의 높낮이가
실루엣에 거의 안 나타나는데, 흔들려면 원판을 24조각에서 수백 조각으로 쪼개야
합니다 — 폰에서 그 값을 내고 얻는 것이 없습니다.

## 캐릭터를 화면 한가운데보다 조금 아래로

가운데에 두면 발밑에 보이는 것과 앞에 보이는 것이 같은 넓이라 가는 쪽이
답답합니다. 카메라가 보는 점을 **1.15m 앞(−Z)** 에 두어 캐릭터를 그만큼
내렸습니다.

```
실측  발 0.66   머리 0.59    (0.5 가 한가운데)
```

몸 한가운데가 0.62입니다. 어깨 너머에서는 안 옮깁니다 — 그쪽은 카메라가 거의
수평이라 같은 값이 하늘을 비춥니다.

## 확인용 배치에 죽은 갈래가 있었습니다

`match` 에 `"balance"` 가 **두 번** 들어가 있었습니다. GDScript 는 먼저 오는
것만 도므로, 뒤에 붙인 것은 영영 실행되지 않습니다 — 풀장 크기를 재려고 넣은
줄이 아무 것도 안 찍어서 알았습니다. 앞엣것을 지웠습니다.

## 고함의 몸이 소리보다 늦게 왔습니다

팔을 뒤로 뻗는 자세가 **다 끝나고 나서야** 나왔습니다. 자세를 `_shout_hold`
하나로 켜고 있었는데 그 값은 **떼는 순간**에 걸립니다 — 누르는 동안 내내
평소대로 서 있다가, 소리와 부채꼴이 다 자란 뒤에 팔이 갔습니다. 모으는 그림이
통째로 빠져 있었던 셈입니다.

모으는 중과 지른 뒤를 **한 갈래로** 묶었습니다. 둘이 이어져 있어야 팔이 도중에
한 번 돌아왔다 다시 가지 않습니다.

**이동 속도도 같은 이유로 틀려 있었습니다**(`_swing_time > 0` 에 묶여 있어
모으는 동안은 평소 속도). 이제 모으는 내내 평소의 0.2배입니다 — 걸어 다니며
모았다가 좋은 자리에서 떼면 그만이면 모으는 일에 값이 없습니다. 0 으로 묶지
않은 것은 그러면 예고를 보고 굴러 피하는 것과 겨룰 수가 없어서입니다.

실측: 0.62 m/s(평소 3.10), 자세 가중치는 모으는 내내 1.00.

## 적1_박치기의 돌진 예고를 선으로

고리 넷을 앞으로 늘어놓던 것을 **두꺼운 선 하나**로 바꿨습니다. 뜻은 맞았지만
넷이 각자 커졌다 사라져서 화면이 어수선했고, **고리 사이의 빈 곳이 안전해
보였습니다** — 실제로는 그 사이도 전부 지나갑니다.

굵기는 눈으로 고르지 않고 **맞는 폭에서 뽑습니다**(1.05m = 내 반지름 + 주인공
반지름 + 손끝 여유의 두 배). 닿았는지 보는 코드와 같은 값이라, 몸이 커지면 선도
같이 두꺼워집니다.

## 굽는 도구가 조용히 끊겨 있었습니다

폴더를 정리하면서(v0.33) `assets/models` 가 `assets/characters` 가 되고 조각
클립이 `art_src/src` 로 나갔는데, **`tools/make_kids.py` 의 경로가 안
따라왔습니다.** 없는 폴더를 보고 있었으니 다음에 캐릭터를 구우려 했으면 그때
막혔을 것입니다.

파일 이름이 두 벌이 된 것도(test3 는 `seojin`, 게임은 `foe_charger`) 표로
옮겨 담았습니다. 고친 뒤 한 캐릭터를 다시 구워 보니 **바이트까지 같은 파일**이
나왔습니다 — 도구가 제대로 이어졌고 결과도 재현됩니다.

## 층을 만드는 한 프레임 — 78ms 에서 19ms 로

프레임 기록이 「층시작」을 가장 나쁜 프레임으로 짚어서, 그 안을 마디마디
쟀습니다. **소품이 압도적**이었고(30.5ms), 그 안은 **거의 전부 `load()`**
였습니다(28.4ms). 심는 것은 0.2ms 입니다.

층을 넘길 때 소품을 전부 지우니, 그 `PackedScene` 을 아무도 안 들고 있게 되어
Godot 이 캐시에서 버립니다 — **다음 층에서 디스크를 다시 읽습니다.** 적도
같습니다.

붙잡아 두고, 제목 화면에서 미리 읽습니다.

```
        전      후
소품   30.5    1.0
적     15.3    2.3
합     78.2   19.0
```

**폴리곤 줄이기와 풀링은 아직 답이 아닙니다.** 캐릭터가 2만 삼각형이지만 화면에
그려지는 것은 프레임당 24~56천뿐이고(카메라가 방 하나만 봅니다), 심는 값은
0.2ms 라 되쓸 것이 별로 없습니다. **값은 심기가 아니라 읽기에 있었습니다.**

남은 것은 던전 벽 메시를 만드는 6.8~9.6ms 입니다. 그건 읽기가 아니라 만들기라
다른 방법이 필요합니다.

## 옵션 판이 떠 있는데 스킬이 눌리던 것

판을 열면 화면 버튼을 **감추고** 있었습니다. 그런데 `visible` 은 **그리기만**
끕니다 — `_input` 은 그대로 돕니다. 게다가 터치는 **가장 가까운 버튼**으로
보내므로(정확히 눌러야 먹으면 폰에서 못 씁니다), 판 위를 눌러도 스냅 반경 안이면
스킬이 같이 나갔습니다.

```
        옵션 열림    숨 100 -> 2     (스킬이 나감)
고친 뒤  옵션 열림    숨 100 -> 100
대조군   옵션 닫힘    숨 100 -> 2     (나가야 정상)
```

감춰지는 순간 잡고 있던 버튼도 놓습니다 — 누른 채로 판이 열리면 뗌 신호가 영영
안 와서 그 버튼이 눌린 채로 남습니다.

**재는 자리를 두 번 고쳤습니다.** 눈대중으로 찍은 자리는 스냅 반경 밖이라 아무
일도 안 일어났고, 자리를 버튼 한가운데로 바꿔도 여전히 안 났습니다 —
`Input.parse_input_event` 로 넣은 터치가 이 짜임에서는 `_input` 까지 오지
않아서였습니다. **핸들러를 직접 불러야** 고친 것을 확인할 수 있었습니다. 그
전까지는 "고치기 전에도 안 눌린다" 는 결과가 나와서, 하마터면 「원래 문제가
없었다」로 답할 뻔했습니다.

## 프레임 기록 — 폰에서 담아 파일로 내보냅니다

깃허브 페이지는 **정적**이라 서버로 못 보냅니다. 그래서 브라우저 안에 담았다가
파일로 내려받게 했습니다 — 옵션 판의 「기록」을 켜고 한 판 한 뒤 「내보내기」.

최근 1800프레임(30초)에 **그때 무슨 일이 있었는지**를 같이 답니다 — 적죽음 ·
고함 · 구르기 · 밀기 · 자동차 · 층시작 · 교환창. 나쁜 프레임(33ms 넘김) 옆에
무엇이 있었는지를 세면 **원인이 이름으로 나옵니다.**

통째로 안 내보냅니다. 1800줄을 폰에서 넘겨 보게 하면 아무도 안 읽습니다 — 나쁜
프레임 열둘과 요약만 냅니다.

데스크톱에서 3층을 1480프레임 돌린 결과:

```
평균 7.1ms (141 fps)  가장 나쁜 86.3ms
33ms 넘긴 프레임 2개
나쁜 프레임 옆에 있던 일:  층시작 1번

   ms  그리기  노드  적  층  무슨 일
 86.3    132    536   6   3  층시작
```

**데스크톱에서도 층을 만드는 순간이 86ms** 입니다. 폰에서는 이 표가 훨씬 길게
나올 것이고, 거기 적힌 이름이 다음에 손볼 자리입니다.

## 배경음이 겹쳐 들리던 것

게임 안에는 재생기가 **하나뿐**입니다(층을 넘고 다시 시작해도 — 재서 확인).
겹친다면 브라우저 쪽입니다.

내보낸 HTML 에 심어 둔 조각이 **여태 만들어진 오디오 컨텍스트를 전부** 깨우고
있었습니다. 폰에서 컨텍스트가 다시 만들어지면(소리가 끊겼다 돌아올 때 그럽니다)
옛것까지 같이 울립니다 — 같은 곡이 어긋난 채로 둘.

새 것이 생기면 앞엣것을 **재우고**, 깨울 때는 **가장 최근 것만** 깨웁니다.
브라우저 없이 두 컨텍스트를 흉내 내 확인했습니다:

```
새 것이 생긴 직후  옛것=suspended  새것=suspended
화면을 만진 뒤     옛것=suspended  새것=running   도는 것 1개
```

곁다리로 `bgm1.ogg` 가 아무도 안 읽는데 빌드에 실려 나가고 있어서 뺐습니다.

## 잡은 뒤 던지기가 안 먹던 것

집은 직후 0.30초 동안 던지기를 막고 있었습니다. "손에 붙는 것을 보고 나서
던져야 두 동작으로 읽힌다" 는 뜻이었는데, 그 사이에는 **화면에도 소리에도
아무것도 없습니다** — 버튼이 씹힌 것으로만 느껴집니다.

```
손에 든 뒤 던지기가 먹기까지
전   0.32초
후   0.07초
```

원래 막으려던 것은 「한 번의 누름이 집기와 던지기를 다 하는 것」인데, 그건 이미
다른 데서 막고 있었습니다 — 집는 누름은 집기가 먹고, 던지기는 다음 누름이며
큐에도 안 넣습니다. 남긴 0.06초는 눌림이 한 번 튈 때를 위한 최소한입니다.

**재는 자리를 한 번 틀렸습니다.** 처음에는 「손에서 떠나는 때」로 쟀는데, 던지기는
0.22초짜리 예비동작이 끝나야 물건이 떠납니다 — 그 길이까지 섞여 "영영 안
던져진다" 로 나왔습니다. 손이 느끼는 것은 **누름이 먹는 순간**입니다.

## 적이 죽을 때 끊기던 것 — 조각마다 노드를 만들고 있었습니다

`Fx.burst` 가 조각 하나마다 `MeshInstance3D` 를 만들었습니다. 열여섯 개면 노드
열여섯에 트윈 열여섯이고, **그리기 호출이 열여섯 번** 늘어납니다 — 전부 반투명·
가산 합성이라 폰에서 특히 비쌉니다.

`MultiMesh` 하나로 담으니 **한 번의 그리기**로 끝납니다.

```
빈 방에서 16조각짜리를 네 번
        그리기          노드
전   89 -> 153 (+64)   403 -> 467 (+64)
후   92 ->  96 (+4)    403 -> 408 (+5)
```

**열여섯 배**입니다. 적이 여럿 한꺼번에 죽으면(밀림 연쇄·자동차·고함) 예전에는
그만큼 곱해졌습니다.

**`_die` 자체는 싼 일이었습니다**(0.6~1.6ms). 값은 그 뒤 0.45초에 있었고, 그래서
「죽을 때 끊긴다」로 느껴졌습니다 — 죽는 코드를 아무리 들여다봐도 안 보이는
자리였습니다.

재다가 한 번 헛짚었습니다. 죽는 순간 그리기가 111 → 127 → 141 로 뛰길래 조각인
줄 알았는데, **확인용 배치가 떨군 사탕이 쌓인 것**이었습니다(아무도 안 줍습니다).
빈 방에서 조각만 따로 터뜨려야 답이 나왔습니다.

## 폰 전체화면 — 안드로이드는 한 번의 터치로, 아이폰은 안 됩니다

**아이폰은 방법이 없습니다.** 애플이 웹 페이지에 전체화면 API 를 안 열어 줍니다
(영상만 됩니다). 「홈 화면에 추가」가 번거로운 것이 맞지만, 그게 아이폰 사파리에서
전체화면으로 가는 **유일한 길**입니다.

**안드로이드는 됩니다.** 화면을 처음 만지는 순간 자동으로 전체화면이 됩니다 -
설치도 버튼도 없습니다. 전체화면은 사용자가 만진 그 순간에만 걸 수 있어서
(브라우저 규칙), `touchend` 를 한 번만 듣고 스스로 떨어지는 조각을 넣었습니다.
데스크톱에서는 안 겁니다 - 마우스로 열었는데 갑자기 전체화면이 되면 놀랍니다.

아이폰에서만 아래쪽에 한 줄이 7초 떴다 사라집니다: 「공유 → 홈 화면에 추가하면
전체화면」. 없는 기능을 되는 척하는 것보다 되는 길을 한 번 알려 주는 편이 낫습니다.

높이도 `100dvh` 로 바꿨습니다. 아이폰은 주소창이 접혔다 펴지면서 `100%` 가 화면
보다 커지는데, `dvh` 는 그때그때의 실제 높이라 아래가 안 잘립니다.

## 밀기 Lv3 — 표시를 잔상 하나로

같은 순간에 셋이 겹쳐 있었습니다: 밀린 적의 **보라 잔상**, 아이 뒤의 **파란
아지랑이**, 그리고 **밀려나는 몸** 자체.

밀려나는 몸이 이미 크게 움직이는 그림입니다. 거기에 자국까지 겹치면 **무엇이
몸이고 무엇이 자국인지** 흐려지고, 보라색은 이 게임에서 다른 데 안 쓰던 색이라
튀었습니다.

남긴 것은 **달려드는 동안의 파란 잔상** 하나입니다. 그건 기술이 나가기 **전**에
보이므로 밀리는 그림과 안 겹칩니다.

걷어내면서 아무도 안 쓰게 된 것들도 같이 지웠습니다 — `Enemy.start_ghost_trail`
(55줄), `Fx.shimmer`(58줄), `SHOVE_GHOST` 색, `Player._picks`.

## 해상도 기본을 60% 로

0.75 로 시작했다가 내렸습니다.

```
100%   92만 픽셀
 75%   52만 픽셀
 60%   33만 픽셀   ← 기본 (100% 의 36%)
```

## 「원본이 무거워서 아니냐」 — 반은 맞았습니다

**삼각형은 아니었습니다.** 캐릭터 하나가 2만 삼각형인데, 실제로 그려지는 것은
**프레임당 24~56천**뿐입니다. 카메라가 방 하나만 보므로 나머지는 걸러집니다.

**텍스처에는 한 자리 있었습니다.** 물물교환 아이만 규격에서 빠져 있었습니다 —
다른 일곱은 1024 + VRAM 압축인데 그 하나만 **2048 무압축**이었습니다. 나중에
들어온 모델이라 폰 규격을 매길 때 없었고, 그 뒤로 아무도 안 봤습니다.

2048² 무압축은 VRAM 에서 16MB(밉맵까지 21MB), 1024 + ETC2 는 0.7MB 입니다.

```
3층 텍스처   50MB -> 32MB
```

폰이 올릴 압축 텍스처를 전부 더해도 15MB 입니다. 화면에 뜨는 나머지는 **렌더
타깃**이고, 그건 해상도가 줄이는 몫입니다.

**그래서 둘 다 필요했습니다.** 해상도는 픽셀과 렌더 타깃만 줄입니다 — 삼각형·
드로콜·텍스처 VRAM·CPU 는 그대로입니다. 텍스처는 원본 규격의 문제였고요.

## 폰에서 뜨겁고 느려지는 것 — 픽셀입니다

**웹이라서가 아닙니다.** 웹은 `gl_compatibility` 렌더러라 데스크톱보다 오히려
덜 그립니다. 그리고 **안 쌓입니다** — 7200프레임을 돌려도 고아 노드 0 입니다.

층마다 느는 것은 텍스처(24 → 45MB, 새 적 종류가 들어와서)이고, 그리기 수는
거의 그대로입니다(92 → 99).

가장 큰 값은 **그리는 픽셀 수**입니다. 브라우저는 화면의 물리 해상도로 캔버스를
잡으므로 2400×1080 폰에서 매 프레임 260만 픽셀을 칠합니다. 벽은 통째로
반투명이라 겹쳐 칠하는 몫까지 붙습니다. **그 값이 그대로 열이 되고, 뜨거워지면
기기가 스스로 성능을 낮춰 나중에 더 느려집니다.**

3D 만 작게 그리고 늘려 붙입니다(0.75). 글자와 버튼은 원래 해상도 그대로입니다.

```
100%   92만 픽셀   텍스처 71MB
 75%   52만 픽셀   텍스처 50MB
```

옵션 판의 「해상도」에서 100~50% 를 돌려 가며 고를 수 있습니다. 폰마다 여유가
다르고, **데스크톱 GPU 로는 폰의 픽셀 비용을 잴 수 없어서** 직접 눌러 보는 것이
가장 빠른 측정입니다.

## 멈춤이 아무것도 안 멈추고 있었습니다

물물교환 창을 띄워 놓고 고르는 동안 판 시간이 계속 갔습니다.

`Game` 은 `PROCESS_MODE_ALWAYS` 입니다 — 멈춘 화면에서도 카메라와 HUD 를 그려야
하니까. 그런데 `process_mode` 의 기본값이 **물려받기**라, 그 밑의 판·주인공·적이
전부 같이 ALWAYS 가 됩니다. **`get_tree().paused` 를 켜도 아무것도 안 멈췄습니다.**

티가 안 났던 것은 적이 **스스로** 단계를 보고 서 있었기 때문입니다. 그 가드가
있는 것만 멈춘 것처럼 보였고, 없는 것은 그대로 돌았습니다 — 예전에 "책을 읽고
고르기도 전에 맞는" 일이 있어 적에게 그 가드를 넣은 적이 있는데, 그게 이 문제의
증상이었습니다.

```
전   적 0.000m 움직임,  시계 +2.67초
후   적 0.000m 움직임,  시계 +0.00초
```

**재는 자리도 한 번 속았습니다.** 확인용 배치는 `phase == PLAYING` 일 때만
돌아서, 창을 열면 프로브 자체가 멈춥니다 — 그것을 "판이 멈췄다" 로 읽을
뻔했습니다. 창이 떠 있는 동안을 보려면 그 밖에서 봐야 합니다.

## 적 체력 바가 줄지 않고 있었습니다

바는 있었고 `scale.x` 도 맞았는데(1.00 / 0.55 / 0.20) 화면에서는 색만
바뀌었습니다. **빌보드가 `scale` 을 버립니다** — 회전을 카메라 것으로 바꿔치면서
`billboard_keep_scale` 이 꺼져 있으면 크기까지 같이 지웁니다.

**재는 법이 두 번 틀렸습니다.** `scale.x` 만 보면 버려진 것을 못 봅니다. 바의
모서리를 `unproject_position` 으로 재도 그건 노드 변환이지 그려진 것이 아닙니다 —
고치기 전에도 같은 숫자가 나와서 하마터면 "이미 되고 있다" 로 넘길 뻔했습니다.
같은 씨앗으로 켬/끔 두 화면을 찍어 diff 하니 다른 곳이 **딱 바 자리 83 × 56 px**
뿐이었습니다.

## 가리는 가구도 벽과 같이 비칩니다

벽만 사라지고 책장의 뒷모습이 그대로 보였습니다. 벽 셰이더는 **벽면의 축**으로
판정하는데(긴 벽을 통째로 비추려고 만든 규칙), **가구에는 그런 축이 없습니다** —
앞판·옆판·뒷판의 법선이 제각각이라 판마다 다른 답이 나옵니다.

소품은 **자기 자리 하나**로만 판정합니다(`whole_object`). 판이 여럿이어도 답이
하나라 통째로 비칩니다.

고치다 하나 더 나왔습니다. 값을 받는 대상이 `wants_wall()` 뿐이라, 벽에 안 붙는
큰 붙박이(미끄럼틀·풀장)는 **셰이더만 받고 값을 못 받아서** 걷어내는 규칙이 걸린
채로 영영 안 걷혔습니다.

## 고함에서 모으기를 걷어냈습니다

값을 여럿 매달아 놨었습니다 — 모은 만큼 범위, 모은 만큼 숨, Lv3 은 끝까지
모아야 피해. 손에는 결국 **"매번 0.5초를 서 있어야 한다"** 로만 남았고, 그동안
발이 0.2배로 묶이므로 급할 때 못 쓰는 기술이 됐습니다. **판을 정리하는 기술**
이라는 자리와 어긋납니다.

```
전   누르는 만큼 1.29~5.70m,  숨 40(살짝) / 30(끝까지),  0.5초 모으기
후   늘 5.70m / 132도,        숨 10,                     누르면 나감
```

값이 하나가 되니 무엇을 쓸지가 "지금 숨이 되나" 로 단순해집니다. 구르기 40 ·
밀기 30 과 견주면 **가장 싼 기술**이고, 그만큼 자주 씁니다.

최소값(`SHOUT_REACH_MIN` 0.14 / `SHOUT_ARC_MIN` 30도)은 남겨 뒀습니다 — 그림과
판정이 같은 함수를 쓰고 그 함수가 0~1 을 받아 사이를 이어 주므로, 다시 모으기를
넣고 싶으면 그 값만 흔들면 됩니다.

## 숨이 모자라면 머리 위에 「숨 차」

화면 위 알림은 있었지만 **급해서 누르는 순간에는 눈이 몸에 붙어 있습니다** —
화면 위는 보고 있는 자리가 아닙니다.

## 되돌린 것 둘

이번에 코드를 두 번 잘못 잘랐습니다. 줄 번호로 블록을 지웠는데, 그 사이에 다른
함수가 여럿 들어 있었습니다(한 번은 463줄). 둘 다 마지막 커밋으로 되돌리고
**문자열 치환만으로** 다시 했습니다 — 지울 블록의 처음과 끝만 보고 자르면 그
사이에 무엇이 있는지 안 보입니다.

## 차를 거꾸로 타고 있었습니다

**원본 그림이 +Z 를 앞으로** 그려져 있었습니다. Godot 은 -Z 가 앞이라, 타면
아이는 가는 쪽을 보는데 **차만 뒤를 봤습니다**.

쓰는 쪽에서 180도를 더할 수도 있지만, 그러면 이 소품을 돌리는 코드가 늘 때마다
같은 보정을 다시 적어야 합니다. **소품에서 한 번 돌려 둡니다**(`face_flip`) —
그러면 `rotation.y` 가 다른 소품과 같은 뜻이 됩니다.

숫자로는 안 잡혔습니다. 차체가 앞뒤로 대칭이라 메시 가운데가 정확히 0 이었고,
결국 세워 놓고 눈으로 골랐습니다 — 운전대 앞에 앉았는지가 답이었습니다.

## 밀기 Lv3 — 달려드는 동안에도 잔상

밀리는 적 쪽에 붙는 잔상은 **맞은 뒤**의 그림입니다. 달려가는 사이는 평소와
같아서, 계통을 끝까지 판 것이 **기술이 나가기 전까지 화면에 안 보였습니다.**

구르기와 같은 방법으로 거리마다 떨굽니다(0.42m — 달려드는 속도가 구르기보다
느려서 같은 간격이면 뭉칩니다). 밝은 잔상은 피해까지 오른 밀기입니다.

## 자동차에서 다리가 지붕을 뚫고 나오던 것

앉는 자세가 없습니다. **자세로는 못 풉니다** — 어떻게 접어도 발끝이 어딘가로
삐져나오고, 무릎을 굽히면 이번에는 무릎이 나옵니다. 몸은 뼈대 하나에 붙은 메시
하나라 다리만 골라 숨길 수도 없습니다.

**높이로 지웁니다.** 발밑에서 0.62m 아래가 0.30m에 걸쳐 사라집니다 — 자세와
상관이 없습니다. 내리면 원래 재질을 그대로 되돌립니다.

높이는 **프래그먼트에서** 봅니다. 정점 단계에서 보면 스키닝이 언제 적용되는지에
답이 매이는데, 프래그먼트의 `VERTEX` 는 이미 화면에 찍히는 자리라 뼈가 어떻게
움직였든 실제로 그려진 높이가 나옵니다.

## 방마다 두 마리는 많았습니다

바로 물렸습니다 — 방이 여덟인 층에서 **열여섯**이 깔립니다. **1~3** 으로 바꿨고,
그 사이에서 실제 수를 정하는 것은 방 크기입니다(좁으면 하나, 넓으면 셋).

위를 막는 이유는 아래를 두는 이유와 같습니다: 좁은 방에 넷이 서면 들어서자마자
둘러싸이고, 그때는 **무엇을 쓸지가 아니라 어디로 도망칠지**만 남습니다.

## 층이 아니라 반입니다

```
씨앗반 · 나무반 · 햇님반 · 달님반 · 원장실
```

"지하 3층" 은 어디에나 있는 던전이고 "햇님반" 은 어린이집입니다. 적이 전부
또래이고 상인도 또래인 판에서 층까지 어린이집의 말이어야 한 이야기가 됩니다.
마지막이 **원장실**인 것은 아이가 불려 가는 곳이고, 선생님이 거기 있는 것이
설명 없이 읽혀서입니다.

## 관문을 둘로

| 층 | 관문 |
|---|---|
| 3 햇님반 | 베개 아기 |
| 5 원장실 | 선생님 |

예전에는 3층부터 **매 층** 선생님이 섰습니다. 매 층에 두면 벽이 아니라
절차가 됩니다. 베개 아기가 가운데인 이유는 이 적이 **"뒤로 돌아가라"** 하나만
묻기 때문입니다 — 답이 분명해서 관문으로 삼기 좋고, 그 답을 배운 채로
원장실에 갑니다. 일반 등장은 4층부터라 3층의 관문이 첫 베개입니다.

## 첫 화면을 셋으로 줄였습니다

```
시작하기 · 개발자 옵션 · 종료하기

테스트 방과 리그 실험실이 첫 화면에 그대로 있었습니다. 처음 열어 본 사람에게는

먹습니다: 첫 화면에서 눌러 실험실로 떨어지면 무슨 일이 난 것인지 모릅니다.

## 고함 Lv3 — 끝까지 모았을 때만

Lv3 을 찍으면 살짝 눌러도 아팠습니다. 그러면 고함이 **"짧게 자주 지르는 것"**
이 가장 좋은 기술이 되고, 모으는 일이 손해가 됩니다 — 모으기를 넣은 이유가
통째로 사라집니다.

```
Lv1 끝까지        61 -> 61   안 아픔
Lv3 살짝 지름     61 -> 61   안 아픔    ← 새 규칙
Lv3 끝까지        61 -> 41   아픔
```

호랑이도 같은 문턱입니다. **이펙트와 피해가 같이 나와야** 무엇이 아픈 고함인지
화면만 봐도 압니다.

## 고함 효과선 — 흰 선분 다발

소용돌이를 걷어냈습니다. 모양은 그럴듯했지만 **덩어리**라 그 뒤의 적이
가려졌습니다 — 굴러 피할 자리를 보라고 켜 둔 그림이 그 자리를 덮는 셈이었습니다.

흰 선분 열넷을 입에서 앞으로 뻗습니다. **길이·굵기·시작점을 전부 흩뜨리고**,

겹쳤습니다. 마디를 하나 더 둬서 방향과 자리를 같이 돌립니다.

## 잡은 것을 던질 때 소리가 없다시피 했습니다

`throw_whoosh` 는 0.34초짜리 바람 소리라, 몸을 크게 감았다 던지는 동작 끝에서
아무 일도 안 일어난 것처럼 들렸습니다. **미는 소리**로 바꿨습니다 — 던지기는
밀기의 연장이고 이펙트도 이미 밀기 계통에서 뽑습니다. 같은 손이 하는 일이면
같은 소리가 나야 합니다.

## 스킬 창은 이미 멈추고 있었습니다 — 문제는 그 앞이었습니다

재 봤습니다. 창이 뜨면 **다음 프레임이 아예 안 옵니다**(`get_tree().paused`).
그러니 "창이 떠 있는데 게임이 돈다" 는 아니었습니다.

무방비였던 것은 **창이 뜨기 전, 책을 꺼내 돌아서서 펴는 1초 남짓**입니다. 손에는
그것이 "고르는 중에 맞았다" 로 느껴집니다.

거기서 멈출 수는 없습니다 — 멈추면 그 동작 자체가 안 돌아 책을 영영 못 펴고
창도 안 열립니다. 그래서 **동작이 도는 동안 안 맞게** 했습니다(실측: 읽는 중
30 피해 → 체력 100 그대로).

## 끼는 것은 그물만 쳤습니다

**재현을 못 했습니다.** 벽에 붙인 책장 옆, 책장 둘 사이의 좁은 틈 — 둘 다
시도했는데 걸어 나왔습니다(3.61m).

그래서 증상에 대고 고친 것이 아니라 **일반적인 그물**을 쳤습니다: 가려는데
0.30초 동안 못 가고 있으면 옆으로 빼냅니다. 만들다 한 번 틀렸는데, 처음에는
`velocity` 로 "가려는 중" 을 봤습니다 — `move_and_slide` 가 막힌 방향의 속도를
지우고 돌아오므로 **정작 완전히 막혔을 때 0 이 되어** 영영 안 걸립니다. 누른
방향으로 봐야 합니다.

어디에서 끼셨는지(어느 소품, 벽 옆인지 방 한가운데인지) 알려 주시면 그 자리를
그대로 만들어 확인하겠습니다.

## 큰 적1_박치기이 아무 일도 안 하고 있었습니다

던질 소품을 배치에서 뺀 뒤로 **던질 것이 없어서 주우러 걸어 다니기만** 했습니다.
기술이 남아 있는데 아무 일도 안 일어나는 상태였습니다.

적1_박치기과 같은 돌진으로 바꾸되, **길이 굳지 않게** 했습니다.

```
적1_박치기      예고 시작에 방향을 못 박음  →  미리 옆으로 반 발
큰 아이   닿기 0.5초 전까지 따라옴    →  마지막 0.5초에 옆으로
```

같은 돌진인데 **피하는 시점이 반대**라 둘이 서로 다른 문제가 됩니다. 실측
(주인공이 옆으로 계속 걷는 중):

```
남은 1.09초 (예고)   어긋난각   0도
남은 0.52초 (돌진)   어긋난각   0도     ← 여기까지 따라옴
남은 0.43초          어긋난각   2도     ← 굳음
남은 0.19초          어긋난각  30도
```

**거리가 아니라 남은 시간으로 끊습니다.** 거리로 끊으면 빠른 돌진일수록 굳는
순간이 이르게 와서, 같은 0.5초를 주려면 적마다 거리를 따로 적어야 합니다.

**바닥의 띠도 같이 돕니다.** 예고에서만 그리고 달릴 때 따라오면 그려 놓은 띠가
곧바로 거짓말이 됩니다. 굳어 있는 돌진은 달리기 시작할 때 한 번 번쩍이고 사라져도
되지만 — 그 뒤로는 몸이 곧 예고입니다 — 쫓아오는 돌진은 달리는 내내 보여 줘야
어디로 오는지 알 수 있습니다.

## 두 아기가 주인공보다 컸습니다

고함 아기와 붙잡는 아기입니다. **1층에서는 종류 배율이 아예 안 걸립니다** —
`_body_scale` 이 1.0 에서 시작해 층이 깊어지며 제 크기로 갑니다. "1층에서는
주인공과 같은 크기" 라는 뜻이었는데, 재 보니 같지 않았습니다.

```
발~머리뼈    주인공 0.924    두 아기 0.954
```

`girl.glb` · `boy.glb` 를 1.25m 로 정규화했는데도 그렇습니다 — **정규화는 머리
장식까지 세는 겉보기 기준**이라 몸의 크기와 늘 같지는 않습니다(주인공은 머리가
커서 1.25 의 더 많은 몫을 머리가 먹습니다).

층에 안 맡기고 0.91 로 못 박았습니다(`base_scale`). 모든 층에서 **0.868 대 0.924**,
주인공보다 6% 아래입니다.

재는 김에 확인용 배치 하나를 더 만들었는데(`--pose=sizes`), **그것도 두 번
틀렸습니다.** 처음에는 겉보기(AABB)가 다섯 종류 모두 1.680 으로 똑같이 나왔고 —
적에게 달린 예고 판과 그림자가 섞였습니다 — 그다음에는 층을 1 로 못 박아 둬서
큰 아이가 안 커 보였습니다. 뼈로 견주고 지금 층으로 세우니 맞습니다.

세어서 확인했습니다.

## 교환 아이가 커 보이던 것 — 두 번 잘못 쟀습니다

**처음 잰 값은 2.48m 였습니다.** 주인공(1.25)의 딱 두 배라 곧바로 반으로 줄일
뻔했는데, 그 숫자에는 머리 위 2.1m 에 떠 있는 **「물물교환」 팻말**이 들어 있었
습니다. 팻말을 빼니 1.59m 입니다.

**두 번째로 뼈를 재 봤더니 몸은 이미 거의 같았습니다.**

```
발에서 머리뼈까지    교환아이 0.955    주인공 0.924
겉보기(AABB)         교환아이 1.590    주인공 1.250
```

차이는 **모자**입니다. 머리뼈 위로 0.58m 올라갑니다(주인공은 0.33m). 자세를
꺼도 1.59 그대로라 든 팔이 아닌 것도 확인했습니다.

**겉보기를 맞췄습니다**(`scale` 을 `1.25/0.76` → `1.25/0.967`). 나란히 섰을 때
눈에 들어오는 것은 실루엣이라 그쪽을 맞추는 것이 맞습니다 — 대신 모자가 키의
한 몫을 먹으므로 **몸은 주인공보다 19% 작아집니다**(0.750 대 0.924). 모자를 빼고
몸을 맞추는 쪽이 좋으시면 `models.gd` 의 그 한 줄입니다.

0.76 이라는 값은 GLB 접근자의 min/max 를 그대로 읽은 것이었는데, **그 숫자는
노드 변환을 안 셉니다** — 모델 안에서 한 번 더 키워 놓았으면 그려지는 크기와
다릅니다. 이제 화면에서 잰 값을 씁니다.

## 록온은 다시 기본 끔

한 번 켬으로 되돌렸던 것을 물립니다. 켜 두면 **어디를 보고 있느냐로 갈리는
것들**이 통째로 무의미해집니다 — 등 뒤로 돌아가 잡기, 베개 아기의 앞뒤, 굴러
피하기가 전부 그렇습니다.

켰던 이유였던 "껐을 때 밀기가 안 맞는다" 는 록온이 아니라 **각**의 문제였고,
그건 이번에 150°로 넓혀 따로 풀었습니다.

## 고함 — 소리가 적에게 닿는 때가 틀려 있었습니다

**손을 뗄 때 한 번만 판정했습니다.** 0.5초 동안 부채꼴을 얼굴에 대고 있어도
적은 아무 일 없이 때리다가, 마지막 한 프레임에 갑자기 굳었습니다 — 보이는 것과
일어나는 일이 어긋납니다.

모으는 동안 부채꼴 안의 적이 **계속 굳어 있습니다.** 넣는 것은 굳힘뿐입니다 —
피해와 밀어냄은 상태가 아니라 한 방이라, 매 프레임 넣으면 0.5초 모으는 동안
예순 번 들어가 즉사시키고 적을 방 밖으로 날립니다.

**그림도 안 보이고 있었습니다.** 부채꼴과 소용돌이는 누르는 첫 프레임부터
있었는데(실측: 모은 0.20 에 둘 다 있음) 시작 진하기가 0.16 이었고, 그때는
사거리도 최소(×0.14)라 **작고 옅은 것이 겹쳐** 폰에서는 아무것도 없는 것으로
보였습니다. 진하기만 0.34 로 올렸습니다 — 크기를 올리면 살짝 지르는 것과 끝까지
모으는 것의 차이가 없어집니다.

## 소용돌이를 걷어내고 선과 구로

모양은 그럴듯했지만 **덩어리**였습니다. 그 뒤에 있는 적이 가려집니다 — 굴러
피할 자리를 보라고 켜 둔 그림이 그 자리를 덮는 셈이었습니다.

선 다섯이 부채꼴 각을 그대로 나눠 퍼지고, 그 위를 구가 셋씩 흘러 나갑니다.
사이가 비어 있어 **뒤가 그대로 보입니다.** 판정은 바닥의 부채꼴이 이미 칠하고
있으니, 이쪽은 "소리가 나간다"만 말하면 됩니다.

**선은 입에서 바닥의 부채꼴 테두리로 내려갑니다.** 처음에는 입 높이에서 수평으로
뻗었는데 화면에서 부채꼴 **밖으로** 나갔습니다 — 내려다보는 카메라에서는 높이
뜬 선의 끝이 더 멀리 찍힙니다. 부호도 재서 골랐습니다(`+X` 로 돌리면 `-Z` 가
위로 올라갑니다 — 한 번 하늘로 뻗었습니다).

## 「구르기 · 구르기」

스킬 카드 제목이 두 번 나왔습니다. 예전에는 계통 안에 스킬이 여럿이라
「밀기 · 억센 손」처럼 둘을 붙여 적었는데, 여섯 계통으로 줄이면서 **두 이름이
같아졌습니다.** 같으면 하나만 적습니다.

## 록온을 끄면 밀기가 안 맞던 것

각이 문제였습니다. 록온이 꺼져 있으면 조준은 **가는 쪽**인데(폰에는 마우스가
없습니다), 잡기 각이 76°(±38°)라 옆에 붙은 적을 밀려면 그쪽으로 걸어가면서
눌러야 했습니다. **가까울수록 나빠집니다** — 2.6m 밖에서는 38° 안에 들지만
0.6m 앞에서는 조금만 어긋나도 벗어납니다.

록온을 끈 동안만 **150°** 로 넓혔습니다(실측: 닿는 각 38° → **75°**).

넓혀도 손해가 없는 것은 **고리가 거짓말을 안 하기 때문**입니다 — 고리는 이
판정과 같은 함수로 고른 대상 아래에 깔려서, 각이 넓어지면 고리도 같이 넓어집니다.
무엇이 밀릴지는 누르기 전에 보입니다.

**그냥 넓히면 안 됩니다.** "가장 가까운 것" 으로 고르면 정면 1.2m 를 겨누고
눌렀는데 어깨 뒤 0.9m 가 밀립니다. 각을 거리로 환산해 더해서 고릅니다(60° 벌어진
적은 1.05m 더 먼 것으로 칩니다).

고치다 하나 더 나왔습니다. 점수의 출발값을 사거리로 두었더니 **닿는데 점수만
넘는 적**(2.4m 40°)이 조용히 빠졌습니다 — 닿는지와 고르는 것은 다른 일이라
따로 둬야 했습니다.

## 풀장을 상점으로 합쳤습니다

같은 방에 값을 받는 자리가 **둘**이었습니다 — 물놀이터(사탕 20, 체력·숨 회복)와
물물교환하는 아이. 그런데 **같은 버튼으로 열렸습니다.** 어느 쪽이 열릴지를
반걸음 차이가 정해서, 물가에서 누를 때마다 다른 것이 나왔습니다. "가까운 쪽이
이긴다" 로 고쳐 봤지만 그건 **규칙을 손이 알 수 없는 자리**로 옮긴 것뿐이었고,
아이의 반응 거리를 3.2 → 1.7m 까지 좁혀야 겨우 갈렸습니다.

**풀장 = 아이 = 상점**으로 합쳤습니다. 물가 어디에서 잡기를 눌러도 같은 것이
열립니다. 풀장 자체의 회복은 없앴고, 주인공이 물에 들어가던 갈래
(`Player.begin_splash`)도 통째로 걷어냈습니다.

**아이가 풀장 한가운데에 서서 물장난을 칩니다.** 자리를 세 번 옮겼습니다.

```
물 안에 기대앉음      테두리 1.20m 가 아이 키 1.25m 와 거의 같아 가림
테두리에 걸터앉음     보이기는 하는데 풀장 밖에 있는 것으로 읽힘
한가운데에 서서       ← 지금.  발 0.36m, 머리 1.61m
```

높이는 눈으로 안 골랐습니다 — **풀장에게 물어봅니다**(`Prop.water_y()` 0.50m 에서
정강이만큼 0.14m 를 뺍니다). 숫자를 박아 두면 소품 크기를 고친 날 아이만 물 위에
뜹니다.

자세는 주인공이 쓰던 물장난 둘(`SPLASH_A`/`SPLASH_B`)을 0.28초마다 오갑니다.
**다리는 안 건드립니다** — 서 있는 클립이 그대로 돌아서 물속에서 발을 놀리는
것으로 읽힙니다. 물은 튀지만 소리는 안 냅니다: 층 내내 첨벙거리고 있어서 소리까지
내면 방 하나가 통째로 시끄러워집니다.

## 스킬 상한이 5 에서 3 이 됐을 때 못 따라온 것들

계통을 여섯 개 × 3 단계로 줄이면서 **문턱 숫자를 다 안 고쳤습니다.** 이번에
찾아 보니 네 갈래로 갈라져 있었습니다.

**이펙트 문턱을 3 이 아니라 2 로 내려 놨습니다.** 구르기 잔상 · 밀기
아지랑이가 Lv2 부터 떴습니다. 원래 「기존 5레벨 이펙트」로 정한 것들이라
Lv3 의 상인데, 2 로 내리면 **Lv2 와 Lv3 이 눈에 같아 보여** 마지막 한 단계를
찍을 이유가 화면에서 사라집니다. 셋 다 3 으로 되돌렸습니다.

고함 Lv2 의 구슬은 **안 옮겼습니다.** 그건 옛 5레벨 이펙트가 아니라 Lv2 에서
처음 생기는 규칙(밀어냄) 자체의 표시입니다 — 빼면 새 규칙이 화면에 안 남고,
Lv3 의 호랑이와 같은 자리에 겹치면 서로를 지웁니다.

**필살기가 영영 안 열려 있었습니다.** `NEED_FAMILY_LV := 5` 인데 `MAX_LV` 가
3 이라 `unlocked()` 가 늘 false 였습니다. 게이지도 안 뜨고 명령(구르기 → 잡기 →
고함)도 안 먹었습니다 — 계통을 끝까지 판 보상이 아무것도 없던 이유입니다.
문턱을 3 으로 내리고, 그 조건이 훑는 계통 목록에 남아 있던 `"passive"`(개편에서
사라진 이름)를 여섯 계통 전부로 바꿨습니다.

**물물교환에서 산 것이 스킬 한 번에 증발했습니다.** 이건 찾다가 나온 것인데
값이 제일 큽니다. `_recompute()` 가 레벨 표에서 **절대값으로 새로 씁니다.**

```
max_hp      = 100 + 40*lv     ← 두꺼운 조끼 +25 가 사라짐
move_speed  = 3.1 * [...]     ← 새 운동화 +0.29 가 사라짐
breath_regen= [0,12,24,40]    ← 박하 사탕 +8/초 가 사라짐
```

사탕 40~46 개를 내고 산 것이 다음 축복 한 번에 없어졌습니다. 산 몫을 따로 들고
표 위에 더합니다(실측: 산 뒤 125/3.39/8.0 → 스킬 찍은 뒤에도 125/3.39/8.0).

**아무도 못 올리는 능력치 다섯 개**가 식 안에 남아 있었습니다 — `shout_stun` ·
`attack_rate` · `lifesteal` · `prop_blast` · `slam_stun`. 늘 0 이거나 1 인 항이
섞여 있으면 다음에 읽는 사람이 "찍으면 오르는 값" 으로 잘못 봅니다. 걷어냈고,
그 값으로만 돌던 메다꽂기(`_slam_landing`)도 같이 뺐습니다.

## 구르기가 방을 반쯤 건너던 것

기본 1.40m 에 Lv3 이면 2.66m 였습니다. **방을 6~9 칸(9~13.5m)으로 줄인 뒤로는
한 번 구르면 방 절반**입니다 — 그러면 굴러 피하기가 "아슬아슬하게 비키는 것"
이 아니라 그냥 자리를 뜨는 것이 됩니다.

기본을 1.12m 로(`DASH_SPEED` 5.0 → 4.0), 단계마다 오르는 몫을 10% 포인트씩
낮췄습니다(30/60/90 → 20/50/80).

```
        전                후
Lv0   1.40m            1.12m
Lv3   2.66m            2.02m
```

## 밀려 날아가는 적은 지정할 수 없습니다

밀어 놓고 그 자리에서 한 번 더 걸 수 있었습니다. 그러면 밀기가 "한 번 세게"
가 아니라 **계속 띄워 두는 것**이 되고, 밀어낸 뒤에 자리를 잡는다는 이 기술의
값이 통째로 사라집니다.

록온과 밀기가 **같은 함수 하나**(`Enemy.is_targetable()`)를 봅니다. 따로 두면
"몸은 그쪽을 보고 있는데 안 밀리는" 상태가 생깁니다. 못 미는 상대에게 몸이
돌아가 있으면, 정작 다음에 밀 상대에게서 등을 돌린 셈이 됩니다.

밀림은 0.45 초입니다(실측: 민 직후 지정 불가, 0.45 초 뒤 다시 가능).

## 방을 줄이니 적도 줄었습니다 — 한 줄로 묶어 뒀습니다

```
판    34~44칸        →  28~36칸
방    8~13 × 7~12칸  →  6~9 × 5~8칸   (12~19.5m → 9~13.5m)
적    3 + 층         →  1 + 층        (1층 4 → 3, 5층 9 → 7)
```

예전 방은 초당 3.1m 로 가로지르는 데 4~6초가 걸렸는데, 그 안에 적이 한둘이면
**방 하나가 곧 빈 마당**입니다. 좁으면 들어서자마자 마주치고, 물러날 곳이 적어
밀기·구르기의 자리 선택이 실제로 의미를 갖습니다.

**판도 같이 줄였습니다.** 방만 작게 하고 판을 그대로 두면 줄어든 만큼이 도로
복도가 됩니다.

적 수는 숫자를 두 군데 적는 대신 **방 크기가 상한을 정하게** 했습니다
(`FOE_ROOM_TILES`, 26칸에 한 마리). 따로 적어 두면 나중에 방을 다시 손볼 때
한쪽만 바뀌고, 좁아진 방에 예전 수가 그대로 들어가 서로 겹쳐 섭니다.

## 고함이 소리와 어긋나 있었습니다

소리 파일이 1.05초라 모으는 시간을 거기 맞췄는데, **귀로는 0.86초에 이미
끝납니다.** 봉우리 크기의 절반 아래로 떨어지는 때를 재서 확인했습니다 — 뒤의
0.19초는 잦아드는 꼬리입니다. 그 사이에도 부채꼴이 계속 자라니, 언제까지 눌러야
하는지를 귀로 알 수 없었습니다.

```
소리가 나는 구간   0.00 ~ 1.03초
봉우리의 50% 아래  0.86초   <- 이 값에 맞춤
```

0.86초에 떼면 모은 정도가 정확히 1.00 입니다.

**시작도 거의 점으로 줄였습니다**(사거리 ×0.55 → ×0.14, 각도 62° → 30°). 시작이
이미 절반이면 모으는 일이 "조금 더 넓어진다" 밖에 안 됩니다.

물어보신 자원 문제는 **숨을 모은 만큼 받는 것**으로 풀었습니다(30% ~ 100%).
거의 안 닿는 고함에 온 숨을 내면 살짝 누르는 일이 그냥 낭비가 되고, 그러면
"짧게 지를 수도 있다" 는 선택이 사라집니다.

```
살짝  사거리 1.08m  각도  36도  숨 10
끝까지 사거리 5.70m  각도 132도  숨 28
```

## 미끄럼틀을 뺐습니다 — 풀장은 혼자서도 말이 됩니다

한 벌로 묶자고 했다가 물러났습니다. 미끄럼틀은 **어느 자리에 두어도 커서 시야를
막고**, 무엇보다 타고 내려오는 그림이 없으면 옆에 서 있는 큰 물건일 뿐입니다.

대신 풀장에 **들어가서 물장난을 치게** 했습니다. 회복이 숫자로만 일어나면 그
자리가 무엇을 하는 곳인지 화면에 안 남습니다 — 값을 치른 것이 몸으로 보여야
다음 층에서도 찾아갑니다.

자세는 둘을 0.28초마다 오갑니다. 한 자세만 두면 물에 서서 팔을 든 채로 굳은
그림이 됩니다 — **물장난은 움직임 자체가 그림**입니다.

## 금화를 사탕으로, 상점을 물물교환으로

상인을 **또래 여자아이**로 바꿨습니다(`witch.fbx`). 예전 상인은 어른이었는데,
적이 전부 또래인 판에서 도와주는 쪽만 어른이면 **어린이집 안의 일이라는 것이
흐려집니다.** 화면에는 「물물교환」과 함께 **"어린이집에도 아군은 있다."** 가
뜹니다.

파는 사람과 사는 사람이 아니라 같은 처지의 아이 둘이 가진 것을 바꾸는
자리이므로, 재고도 또래가 가질 만한 것으로 갈았습니다 — 딸기 우유, 단단한
주먹밥, 새 운동화, 돋보기, 박하 사탕.

**물놀이터는 유료로 바꿨습니다**(사탕 20). 바로 옆에 물물교환하는 아이가 있어서,
같은 사탕을 **지금 쉬는 데 쓸까 다음 층을 위해 쓸까**가 그 자리에서 갈립니다.
공짜면 그 선택이 사라지고, 들르는 것이 늘 이득인 절차가 됩니다.

둘을 같은 방에 두니 **상호작용이 겹쳤습니다** — 물가에 서 있는데 교환 창이
열렸습니다(아이의 반응 거리 3.2m 가 둘 사이 거리 2.9m 보다 넓었습니다). 순서로
정하던 것을 **가까운 쪽이 이기게** 고쳤습니다.

## 고함을 누르는 만큼 커지게 했습니다

누르면 모으기 시작하고 **떼는 순간** 지릅니다. 길이와 넓이가 같이 자랍니다
(사거리 ×0.55 → ×1.0, 각도 62° → 132°).

**모으는 시간을 고함 소리의 길이(1.05초)에 맞췄습니다.** 살짝 눌렀다 떼면
소리도 거기서 끊깁니다 — 귀와 눈이 같은 것을 말하므로 언제까지 눌러야 하는지를
따로 배울 필요가 없습니다. 소리를 끊으려고 `Sfx.play_loose` 를 새로 만들었습니다
(기존 `play` 는 내고 잊는 것이라 손잡이가 없습니다).

숨은 더 안 받습니다. **모으는 시간 자체가 값**입니다 — 그동안 서 있어야 하고
적은 그 사이에 다가옵니다. 그리고 숨은 누를 때 **확인만** 하고 실제로 빼는 것은
지를 때입니다: 모으다 그만두는 일이 값을 치르는 일이 되면 잘못 눌렀을 때 손해가
두 번입니다.

실측: 4.8m 앞의 적을 살짝 누르면 못 맞히고(3.70m), 끝까지 누르면 맞습니다(5.70m).

## 벽을 「같은 축 전부」로 만들었더니 화면이 깨졌습니다

말씀대로 축을 따라 벽면 전체가 비치게 했는데, **그 축은 지도 끝까지
이어집니다.** 가리지도 않는 먼 벽까지 통째로 비쳐서 방이 사라지고 거뭇한 쐐기만
남았습니다 — 보내 주신 화면이 그것입니다.

벽을 따라 **3.4m 를 넘어가면 도로 닫히게** 했습니다. 한 번에 비치는 것은 그 두
배 길이의 벽 한 판입니다. 축을 맞추면서 "벽을 따라 얼마나 떨어졌나" 라는 값을
잃어버린 것이 원인이었습니다 — 맞춘 자리에서는 그 거리가 언제나 0 입니다.

## 자동차가 하늘로 날아간 것

`freeze` 만으로는 부족했습니다. 얼린 차는 **움직이지 않는 벽**이 되는데, 그
벽을 매 프레임 발밑으로 옮기니 물리가 몸을 밖으로 밀어냈습니다 — 빠져나갈 곳이
위뿐이라 하늘로 올라갔습니다.

같은 문제를 **소품에서 이미 푼 적이 있었습니다**(들고 있는 담요에 캐릭터가 날아
가던 것). 그때 만든 `set_solid(false)` 를 그대로 씁니다 — 두 번째 해법을 새로
만들면 다음에 고칠 때 한쪽만 고칩니다. 위쪽 속도도 0 으로 눌러 둡니다.

## 록온을 끄면 게걸음으로 걷던 것

폰에는 마우스가 없는데 `get_mouse_position()` 은 **마지막으로 닿은 자리**를 계속
돌려줍니다. 그래서 록온을 끄면 몸이 조금 전에 누른 버튼 쪽을 향한 채로 굳고,
걸어가는 쪽과 보는 쪽이 따로 놀았습니다.

화면 조작일 때는 **가는 쪽**이 조준입니다. 멈추면 마지막으로 보던 쪽을 그대로
둡니다 — 0 으로 되돌리면 손을 뗄 때마다 몸이 한 방향으로 홱 돌아갑니다.

## 스킬 스무 개를 여섯 개로 줄였습니다

가장 크게 바꾼 것입니다. 예전에는 스킬이 스무 개였고 계통 Lv 은 그것들을 몇 번
골랐는지의 합이었습니다. 그래서 **"밀기를 팠다" 와 "무엇이 세졌다" 가 따로
놀았습니다** — 같은 밀기 Lv3 인데 넉백만 셋 찍은 판과 사거리만 셋 찍은 판이
완전히 다른 게임이고, 고르는 화면에서는 그 차이를 알 수 없었습니다.

지금은 **계통이 곧 스킬**입니다. 여섯 개(밀기·고함·구르기·체력·이속·스테미나),
각 3 단계가 끝. 단계마다 무엇이 붙는지는 표 한 곳에 다 적혀 있어서, 고르는
화면에 "다음 단계에 무엇이 생기는지" 를 그대로 보여 줄 수 있습니다.

단계가 **수치만 올리지 않게** 했습니다. 각 계통의 2단계와 3단계에는 수치가
아니라 규칙이 하나씩 붙습니다 — 연격, 적을 통과, 밀림 연쇄, 층마다 완전 회복,
구른 직후 질주, 한 번 버팀. 수치만 오르면 세 번을 다 찍어도 하는 일이 안
바뀝니다.

### 고치다가 진짜 버그를 하나 잡았습니다

확인용 배치에서 **고함 Lv1 인데 피해가 들어갔습니다.**

```
[균형] 고함 Lv1 뒤 적 체력 29 / 61   (안 깎여야 맞음)
```

레벨을 두 사전에 나눠 들고 있었습니다 — `boon_lv`(스킬별)와 `skill_lv`(계통별).
계통이 곧 스킬이 되면서 둘이 같은 값이 됐는데, `level_of` 는 앞의 것을
`family_level` 은 뒤의 것을 읽고 있었습니다. **한쪽만 고치면 조용히
갈라집니다.** 하나로 합쳤습니다.

## 고함이 너무 좋았습니다 — 피해를 없앴습니다

범위가 넓고, 굳히고, 아프기까지 했습니다. 그러면 다른 기술을 쓸 이유가
없습니다. 이제 **Lv3 을 찍기 전까지 피해가 0** 입니다 — 판을 정리하는 것이 이
기술이 파는 물건이고, 아픈 일은 밀기가 합니다.

범위 표시도 바꿨습니다. 퍼져 나가는 고리 셋을 걷어내고 **판정 그 자체를
칠합니다.** 고리는 "소리가 퍼진다" 는 그림으로는 좋았지만 어디까지 닿는지를 못
가르쳤습니다 — 테두리는 선 위가 위험한 것처럼 읽히고, 셋이 시차를 두고 나가니
어느 고리가 사거리인지도 알 수 없었습니다. 적의 호통이 이미 칠한 부채꼴을 쓰고
있어서, 같은 그림을 같은 뜻으로 쓰면 배울 것이 하나로 줄어듭니다.

## 굴러 피하는 맛이 없던 이유

예고가 끝나는 순간 **거리만** 보고 있었습니다. 그래서 옆으로 굴러 나가도
가까이만 있으면 맞았고, 구르기가 "아슬아슬하게 피하는 것" 이 아니라 **"멀리
도망치는 것"** 뿐이었습니다.

맨손 공격도 예고 시작에 **방향을 굳히고**, 그 부채꼴을 바닥에 칠하고, 끝날 때
그 안에 있는지를 봅니다. 이제 반 발만 옆으로 빠져도 빗나갑니다 — 칠해 둔
부채꼴이 그대로 답입니다. 호통·돌진이 이미 쓰던 규칙을 맨손에도 준 것입니다.

여기에 **재사용 대기를 확 줄였습니다**(구르기 1.1초 → 0.22초). 연달아 구르는
것을 막는 것은 숨(20)이지 시계가 아닙니다 — 시계로 막으면 피해야 하는 순간에
"아직 안 됨" 이 되는데, 그건 실력이 아니라 운입니다.

## 록온을 껐습니다

기본이 켜져 있었습니다(폰이면 자동으로). 편하지만 **겨누는 일이 통째로
사라집니다** — 등 뒤로 돌아가 잡기, 베개 아기의 앞뒤, 그리고 방금 만든 "예고를
보고 옆으로 굴러 나가기" 까지 다 같이 무의미해집니다.

전에 붙잡는 아기가 **영영 등을 못 잡던 것**도 이것 때문이었습니다 — 다가오는
아이가 곧 가장 가까운 적이 되므로 늘 정면에 놓입니다. 그때는 적 쪽 궤도를
고쳐서 우회했는데, 원인은 이쪽에 있었습니다.

옵션 판에서 켤 수 있습니다.

## 상점을 물놀이터로 바꿨습니다

미끄럼틀이 방에 혼자 서 있으면 그냥 시야를 막는 큰 물건이었습니다. 풀장과
한 벌로 묶어 **물에 미끄러져 들어가는 모양**으로 놓고, 그것이 상인 자리를
대신합니다.

상인을 뺀 이유: 금화로 능력치를 사는 일이 **스킬 고르기와 하는 말이
같았습니다**(둘 다 "무엇을 세게 할까"). 층이 다섯뿐이라 두 번쯤 만나고 끝나는데,
그 두 번이 판을 정하지도 않았습니다.

물놀이터는 층마다 한 번 체력과 숨을 다 채웁니다. 값은 금화가 아니라 **가는
수고**입니다 — 시작 방과 출구 사이에 있어서, 들를지 말지가 곧 "돌아가는 길에
적을 더 만날까" 입니다.

## 던지는 소품을 뺐습니다

집어서 던지는 데 두 손과 몇 초가 드는데, 그동안 **밀기를 두 번 하는 편이 언제나
나았습니다.** 쓰이지 않는 물건이 방마다 서넛씩 굴러다니면 밟고 걸리는
잡동사니일 뿐입니다.

우유는 남깁니다 — 던지는 물건이 아니라 마시는 물건이고, 체력이 자원인 이상 방에서
찾아내는 것 자체가 할 일입니다. 함정도 뺐습니다: "여기를 밟지 마라" 만 말하는데,
발을 어디에 두느냐는 **이미 적과 굴러 피하기가 정하고 있습니다.**

대신 **자동차**를 넣었습니다. 타면 3.4초 동안 무적으로 방을 휘젓습니다. 조종은
안 됩니다 — 조종되면 그냥 "빨라지고 무적인 상태" 라 다른 기술이 다 쓸모없어
집니다. 못 모는 대신 아무 대가도 없어서, 몰렸을 때 "도망갈까" 말고 다른 답이
하나 생깁니다.

## 끝을 정했습니다 — 5층

끝없이 깊어지기만 하면 판이 끝나는 길이 **죽는 것뿐**이라, 잘한 판과 못한 판의
결말이 같습니다. 다섯 층이면 스킬을 네 번 고르므로 계통 하나를 끝까지 파고
다른 하나를 맛볼 수 있습니다 — 상한이 3 인 것과 맞물린 값입니다.

적은 **수를 줄이고 한 마리를 세게** 했습니다(1층 6 → 4마리, 배수 ×1.45).
여럿이면 무엇을 하든 밀기 한 번에 무리가 정리되는 것이 답이라, 적 종류를 나눠
만든 것이 화면에서 안 보였습니다.

## 벽을 세 번 고쳐 벽면째로 비치게 했습니다

```
점을 찍어 지움     화면에서 점무늬. 카메라가 움직이면 지글거림
알파 + 칸 단위     긴 벽 한가운데에 창이 난 것처럼 보임
알파 + 벽면 단위   같은 축의 벽이 통째로 비침          ← 지금
```

벽면 단위로 재는 법: 면이 보는 쪽으로 벽이 놓인 축을 알아낸 뒤, **그 축을 따라
자리를 주인공에게 맞춘 점**으로 바꿔 봅니다. 그러면 그 벽의 모든 픽셀이 같은
답을 내므로 벽면 하나가 통째로 비칩니다.

반투명이 캐릭터를 덮는 문제는 남기는 비율(0.18)이 풉니다 — 덧그려져도 18%라
캐릭터가 82%로 비쳐 보이고, 벽이 거기 있다는 것도 같이 읽힙니다.

## 폰 규격 — 줄인 것의 대부분은 텍스처가 아니었습니다

깃허브 페이지로 내보내면서 폰 규격으로 낮췄습니다. 시작은 텍스처였습니다 —
캐릭터가 2048² 인데 화면에서는 60~150 픽셀이라, 1024 로 자르고 VRAM 압축을
켰습니다.

그런데 다시 내보내니 **pck 가 커졌습니다.**

```
57.0MB  →  63.5MB
```

`vram_texture_compression` 이 데스크톱(S3TC)과 폰(ETC2)에 **둘 다** 켜져
있었습니다. 압축 텍스처는 pck 안에서 더 줄지 않으므로, 변형이 둘이면 그대로
두 벌입니다. 폰용 빌드니 데스크톱 쪽을 껐습니다 — 57.0MB, 처음과 같았습니다.

**이 한 줄이 다음 절의 사고가 됩니다.**

**텍스처를 4분의 1로 줄였는데 pck 가 그대로라는 것이 답이었습니다.** 텍스처가
pck 의 주인이 아니었던 것입니다. 무엇이 들어 있는지 재 봤습니다.

```
art_src/source   45MB   소품을 구울 때 쓴 4면도 원본
assets/models   77MB
assets/props    31MB
```

`art_src/source` 는 **주석에만** 나옵니다. 실행 중에 읽는 코드가 없는데
`export_filter="all_resources"` 라 통째로 들어가고 있었습니다. 같이 확인하니
`wall1`·`wall2`(벽지로 갈아탄 뒤 안 씀)와 `tiger.glb`(옆얼굴 그림으로 바꾼 뒤
안 씀)도 그대로 실려 있었습니다.

빼고 나서:

```
텍스처 262MB → 41MB     pck 57MB → 28.6MB     빌드 93MB → 67MB
폰이 실제로 받는 양 34MB (wasm 이 gzip 으로 37.7 → 10.2MB)
```

**파일은 지우지 않고 빌드에서만 뺐습니다**(`exclude_filter`). 지우면 되돌릴 수
없고, `wall1` 은 "일단" 안 쓰는 것이라고 하셨습니다.

## PC 에서 안개만 보인 것 — "폰용" 을 "폰에서만" 으로 만들었습니다

공유하셨더니 **안개 때문에 안 보인다**는 말이 왔습니다. 화면을 보니 UI 는
멀쩡한데 바닥·벽·소품·사람이 전부 사라지고 따뜻한 갈색만 남아 있었습니다.
안개는 원래 있는 것(`fog_density = 0.0045`)이라 안개를 의심하기 쉬웠지만,
안개가 짙어진 게 아니라 **안개 말고 아무것도 안 그려진 것**이었습니다.

PC 라는 말을 듣고 pck 를 열어 봤습니다.

```
etc2 변형이 pck 안에 있나: True
s3tc 변형이 pck 안에 있나: False
```

**데스크톱 GPU 는 WebGL 에서 ETC2 를 못 읽습니다.** ETC2 는 사실상 모바일 전용
형식이고, 데스크톱은 S3TC 를 씁니다. 그러니 VRAM 압축을 건 것 — 바닥·벽·소품·
캐릭터 — 이 통째로 안 올라오고, 압축을 안 건 UI 버튼 그림만 남았습니다.

pck 를 줄이려고 `for_desktop` 을 끈 것이 원인입니다. **"폰용 스펙" 을 "폰에서만
도는 빌드" 로 만들었습니다.** 웹은 폰과 PC 가 같은 주소를 여는 곳이라, 둘 중
하나만 고르는 선택지가 애초에 없었습니다.

둘 다 담아 되돌렸습니다(pck 28.6 → 44.3MB). 줄이려면 `compress/mode=4`
(Basis Universal, 34.9MB)가 남아 있지만, 폰에서 화질을 볼 방법이 없어 **깨진
빌드를 두 번 보내지 않으려고** 안 썼습니다.

고친 뒤 헤드리스 크롬으로 확인했습니다 — 그 브라우저는 데스크톱처럼 S3TC 를
쓰고 ETC2 는 안 쓰므로, 같은 조건입니다.

## 깃허브 페이지 — 헤더를 못 붙이는 곳입니다

주소는 https://2gilhan.github.io/rogue1/ 입니다. 소스는 `main`, 빌드는
`gh-pages` 가지 뿌리입니다.

`main` 에 빌드를 안 담은 이유: 소스를 한 줄 고칠 때마다 30MB 짜리 바이너리가
역사에 한 벌씩 쌓입니다. 되돌릴 수 없는 종류의 무거움입니다.

**하마터면 흰 화면이 될 뻔한 것 하나.** Godot 웹 빌드에 스레드를 켜면
SharedArrayBuffer 를 쓰고, 그러면 `Cross-Origin-Opener-Policy` 헤더가 필요한데
**GitHub Pages 는 응답 헤더를 못 붙입니다.** 이 프로젝트는 이미
`variant/thread_support=false` 였습니다 — 우연히 맞은 것이니, 나중에 누가 켜면
tailnet 에서는 되고 페이지에서만 안 되는 상태가 됩니다.

기존 페이지(`2GILHAN/vtos`)는 **그대로 뒀습니다.** 페이지는 저장소마다 하나씩
뜨므로 서로 밀어내지 않습니다.

## 버튼 뭉치를 구석 쪽으로 옮겼습니다

여백 30 → 16(구르기가 오른쪽 아래로), 두 각도를 **같은 만큼** +22도(고함이
오른쪽으로).

```
전:  고함 230도(왼쪽 위)    밀기 150도(왼쪽 아래)
후:  고함 252도(거의 위)    밀기 172도(거의 왼쪽)
```

**고함만 돌리지 않은 이유**: 그러면 둘 사이가 80도에서 102도로 벌어져,
구르기-밀기 간격과 고함-밀기 간격이 서로 달라집니다. 함께 돌리면 셋 사이의
거리가 예전 그대로이고 바뀌는 것은 뭉치가 놓인 **방향**뿐입니다. 여백도 한
값이 두 변(아래·오른쪽)을 함께 정하므로 구석에 비스듬히 치우치지 않습니다.

가상 원과 두 변을 화면에 겹쳐 그려 확인했습니다.

## 이펙트가 거짓말을 하고 있었습니다

"밀기라면 넉백을 올리는 것도 있고 피해를 높이는 것도 있을 텐데, 어떤 기준으로
이펙트가 생기냐" 고 물으셨습니다. 답은 **계통을 몇 번 찍었나 하나뿐**이었고,
무엇을 찍었는지는 안 보고 있었습니다.

그래서 「긴 팔」(달려드는 거리)만 세 번 찍어도 밀기 Lv3 이 되어, 넉백은 그대로인데
화면에서는 적이 세게 밀려나는 그림이 떴습니다. **화면이 실제로 세진 것과 다른
말을 하고 있었습니다.**

이제 **붙느냐 마느냐는 계통 Lv3, 세기는 그 스킬이 올린 값**입니다.

```
긴 팔 x3          넉백 0.0  피해 0.00  ->  잔상 2장        아지랑이  6조각
밀치는 힘 x3      넉백 2.1  피해 0.00  ->  잔상 5장        아지랑이 12조각
억센 손 x2 + 밀치는 힘   넉백 0.7  피해 0.80  ->  잔상 3장(진하게)  아지랑이 8조각
```

셋 다 밀기 Lv3 입니다. 화면이 갈립니다.

「돌풍」을 안 찍었는데도 맞은 자리에서 구슬이 터지던 것(고함 Lv5 로 켜고
있었습니다)도 **돌풍을 찍었을 때만** 터지게 했습니다.

**호랑이만 계통 Lv5 로 남겼습니다.** 그것은 세기가 아니라 등급입니다 — 계통을
끝까지 판 자리에는 더 센 구슬이 아니라 **다른 그림**이 와야 합니다.

이펙트를 스킬마다 새로 그리는 길(밀기 3 + 고함 4 + 구르기 3 = 열 가지)도
있었지만, 지금 걸린 문제는 "그림이 없다" 가 아니라 **"그림이 틀린 말을 한다"**
였습니다. 세기를 옳은 값에서 뽑는 것으로 그 문제는 사라집니다.

## 던지기가 짧아 보인 데에는 제 몫이 있었습니다

던지기 거리는 이번에 건드리지 않았는데도 짧아졌다고 느끼셨습니다. 재 보니
값은 그대로였고(Lv9 0.86m), **바뀐 것은 밀기 연타를 막은 것**이었습니다.
예전에는 3초에 20번을 밀 수 있어서 넉백이 겹겹이 쌓였습니다 — 한 번의 거리가
아니라 **여러 번의 합**을 보고 계셨던 것입니다.

그래서 한 번의 거리를 올렸습니다. 던지기를 밀기의 **2.5배**로 둡니다.

```
Lv0   밀기 0.29m   던지기 0.86m
Lv9   밀기 0.89m   던지기 2.18m
```

배수는 계산해서 넣었습니다 — 감속이 일정하면 거리는 속도의 제곱에 비례하므로
2.5배를 보내려면 속도는 √2.5 = 1.58배입니다(`THROW_PUSH` 0.70 → 1.11).

한 번 "둘을 같게 맞춰 달라"고 하셨던 것을 다시 벌린 이유: 잡고, 들고, 돌려서
던지는 값을 치르는데 그냥 미는 것과 같은 거리면 **던질 이유가 없습니다.**
여섯 배는 다른 기술로 보이지만 2.5배는 같은 기술의 더 센 쪽으로 읽힙니다.

## 폰 렉 — 데스크톱에서는 재현되지 않습니다

40000프레임(11분)을 돌리며 600프레임마다 찍었습니다.

```
노드 466~605   고아 0   자원 110~141   메모리 107 → 132MB 에서 평평
프레임 시간 7~9ms 로 처음부터 끝까지 같음
```

**쌓이는 것이 없습니다.** 층이 깊어지면 무거워지기는 합니다(적 3 → 33마리,
물리 5.4 → 10.2ms). 다만 폰 설정(글로우·그림자 없음)으로 재면 그리기 횟수는
층과 상관없이 35~45로 거의 같았습니다 — 데스크톱에서 층 때문에 늘어 보이던
것(117 → 301)은 대부분 **그림자 패스**였고, 폰에서는 처음부터 꺼져 있습니다.

여기서 못 재는 것들이 남습니다 — 브라우저의 메모리 증가, 기기 발열로 인한
성능 저하, 웹 빌드에만 있는 무엇. 그래서 **옵션에 「성능」 줄을 넣었습니다.**
느려졌을 때 그 숫자를 알려 주시면 어디를 봐야 할지가 정해집니다.

- **fps 는 그대로인데 「최악」만 크다** → 특정 동작에서 한 번씩 멎는 것
- **노드·메모리가 계속 오른다** → 무언가 안 지워지고 쌓이는 것
- **둘 다 그대로인데 느리다** → 기기 발열이나 브라우저 쪽

## 벽돌은 걷어냈습니다 — 민무늬 회벽 하나로

벽 그림 둘(`wall1` 회벽 / `wall2` 벽돌)을 한 층에 좌우로 갈라 깔아 견줬고,
**회벽으로 정했습니다.** 좌우 가르기와 그 확인용 배치(`--pose=walls`)도 함께
걷어냈습니다 — 견주려고 만든 장치라, 정한 뒤에도 남겨 두면 "왜 지도 절반만
다른가" 를 다음 사람이 다시 밝혀야 합니다.

벽돌이 진 이유는 무늬 자체가 나빠서가 아닙니다. 가로줄이 뚜렷하면 이 그림체
(외곽선과 넓은 단색 면)에서 벽이 **쌓아 올린 것**으로 읽히고, 배경이어야 할
벽이 주인공만큼 눈에 들어옵니다. 회벽은 무늬라기보다 **면의 얼룩**이라
그 자리에 머뭅니다.

`wall2.png`(5.2MB)는 지우지 않고 뒀습니다. 다만 안 쓰는 그림도 빌드에는
그대로 들어갑니다 — 영영 안 쓸 것이면 지우는 편이 폰에서 받는 시간을
줄입니다.

## 밀기에는 적 앞에서만 대기가 없었습니다

"범위 안에 상대가 있으면 연타가 된다"는 말이 정확했습니다. 테스트 방에서 매
프레임 눌러 세 봤습니다.

```
적 있음(3초)   밀기 20회   고함 6회
적 없음(3초)   밀기  4회   고함 6회
```

밀기는 누르는 자리에서 갈립니다 — 달려들 상대가 있으면 대기를 **0.95초의
15%**(0.14초)만 걸고, 없으면 온전히 걸었습니다. 그 짧은 값은 원래 "손에 든 것을
던질 때 버튼이 즉시 먹어야 한다"고 둔 것인데, **던지기는 대기 검사보다 앞에서
갈라집니다**(`_held != null`) — 그 값이 하는 일은 아무것도 없고, 남은 것은 적
앞에서만 대기가 사라지는 것뿐이었습니다.

거기에 손이 닿아 밀친 자리(`_land_lunge`)에서도 대기를 걸지 않아서, 0.14초마다
달려들기가 처음부터 되살아났습니다.

**달려드는 것도 한 번 쓴 것으로 셉니다.** 고친 뒤 4회 / 3회 — 적이 있든 없든
같습니다. 던지기와 우유가 짧은 대기를 그대로 쓰는 것은 그 둘이 검사보다 앞에서
갈라지기 때문입니다.

**고함은 어느 조건에서도 6회였습니다**(0.55초 대기 그대로). 고함 계통을 9까지
올려도 `attack_rate` 는 1.00이라 대기가 줄지 않습니다 — 같이 고칠 것이 없었습니다.

## 벽에 등을 붙이면 생기던 얼룩 — 그림자가 아니었습니다

여러 번 말씀하셨는데 계속 못 잡았습니다. 그림자로 보고 조명 쪽을 뒤졌기
때문입니다. 걷어내기를 끈 판과 나란히 찍으니 한 번에 나왔습니다 — **얼룩이
통째로 사라집니다.** 그림자가 아니라 **벽 걷어내기가 등 뒤 벽에 낸 구멍**이고,
뚫린 자리 뒤에는 아무것도 없어서 검게 보인 것입니다.

셰이더는 "카메라와 캐릭터를 잇는 선 근처"를 걷어냅니다. 그런데 63도로
내려다보는 카메라에서는 **등 뒤 벽의 위쪽이 캐릭터보다 카메라에 가깝습니다** —
높으니까요. 그래서 가리지도 않는 벽이 "사이에 있다"는 검사를 통과했습니다.

높이를 빼고 **바닥에 내려놓고** 보면 둘이 부호로 갈립니다.

```
가리는 벽   캐릭터보다 카메라 쪽   ahead > 0
등 뒤 벽    반대쪽                 ahead < 0
```

세 장을 나란히 찍어 확인했습니다 — 전(얼룩) / 후·등 뒤 벽(깨끗함) / 후·가리는
벽(그대로 비침). 확인용 배치를 남겼습니다(`--pose=wallhug`, `--side=front`).

## 쿨다운이 어디에도 안 보였습니다

기술 셋 다 쿨다운이 있는데(고함 0.55초, 구르기 1초 안팎, 밀기 0.35초) 화면에는
**아무 표시도 없었습니다.** 눌렀는데 아무 일도 안 일어나면 그것이 쿨다운인지
숨이 모자란 것인지 조준이 빗나간 것인지 알 수 없습니다.

버튼과 화면 위쪽 두 곳에 도트 아이콘을 놓고, 남은 쿨다운을 **부채꼴로**
덮었습니다. 12시에서 시계 방향으로 돌아 다 돌면 덮개가 사라집니다.

세 가지를 정하면서 이유가 하나씩 있었습니다.

**남은 쪽을 덮습니다**(찬 쪽을 칠하지 않습니다). "아무것도 없을 때가 쓸 수
있을 때" 가 가장 단순한 규칙입니다. 숫자로 적지 않은 것도 같은 이유입니다 -
급할 때 숫자를 읽을 겨를이 없습니다.

**숨 부족은 다르게 보입니다**(아이콘이 옅어집니다). 쿨다운은 기다리면 차지만
숨은 기다려도 안 됩니다 - 다른 기술을 써야 합니다(연타 벌금). 하나로 합치면
왜 못 쓰는지가 안 읽힙니다.

**위쪽에도 겹쳐 둡니다.** 버튼은 폰에만 있고, 화면 오른쪽 아래라 눈이 가 있는
곳과 멉니다 - 싸우는 동안 시선은 화면 가운데 위쪽, 적이 오는 쪽에 있습니다.

## 버튼 글자를 도트로 바꿨습니다

둥근 버튼에 "밀기(잡기)" 를 넣느라 글자 크기를 이름 길이에 따라 줄이고
있었습니다. 폰에서 안 읽히고, 무엇보다 **읽어야** 압니다 - 급할 때 엄지는
글자가 아니라 모양을 봅니다.

그림 파일을 쓰지 않고 문자열 격자에서 그립니다(`scripts/dot_icon.gd`).

```
const GRAB := [
	"..X.X.X....",
	"..X.X.X.X..",
	"..XXXXXXX..",
	...
]
```

해상도가 달라져도 늘 선명하고(칸을 화면 크기에 맞춰 그립니다), 아이콘을
고치려면 점을 옮기면 됩니다. 색과 자리는 그대로 두었으므로 손에 익은 것은
그대로 씁니다.

도중에 두 가지가 걸렸습니다. `icon.ready = ...` 가 파싱에서 깨졌는데
**`Node` 에 같은 이름의 시그널이 있어서** 그쪽으로 잡혔습니다(`charge` 로
바꿨습니다). 그리고 부채꼴을 아이콘 칸에 맞춰 잘랐더니 **동그란 버튼 안에
검은 네모**가 들어앉았습니다 - 버튼에서는 반지름을 넘겨 받아 버튼 모양을
따라가게 했습니다.

## 새 적 셋에 전용 모델이 들어왔습니다

처음에는 기존 아이 메시(도원·적1_박치기)에 색조만 다르게 입혀 뒀습니다. test3 에서
`baby` / `girl` / `boy` 가 나오면서 셋 다 전용 모델로 바꿨습니다.

| 적 | 모델 | 원본 키 | 잰 보폭 |
|---|---|---|---|
| `pillow` 베개 아기 | `baby.glb` | 0.715m | 0.531 m/s |
| `screamer` 고함 아기 | `girl.glb` | 0.728m | 0.613 |
| `clinger` 붙잡는 아기 | `boy.glb` | 0.754m | 0.555 |

원본이 전부 0.72~0.75m 로 작게 나와서, 게임 안에서 다른 아이들과 같은 키
(1.25m)로 서도록 `Models.SIZE` 에 배율을 적었습니다 - 새 주인공(0.85m)에
쓰던 방법 그대로입니다. 규칙 값(충돌체·사거리)은 `height` 를 쓰므로 그쪽은
건드릴 것이 없습니다.

**보폭은 모델을 바꿀 때마다 다시 잽니다.** 클립을 다시 구운 것과 같은 일이고,
안 재면 스케이팅이 돌아옵니다.

## 베개가 머리에 가려 안 보였습니다

베개를 가슴 높이(키의 0.60)에 몸 바로 앞으로 뒀습니다. 적1_박치기 메시일 때는 보였는데
`baby.glb` 로 바꾸니 **사라졌습니다** - 이 아이는 머리가 훨씬 커서, 내려다보는
63도 카메라에서 머리가 그 자리를 덮습니다.

눈으로 옮기지 않고 뼈를 쟀습니다(`--pose=guard` 가 찍어 줍니다). 키 1.25 기준:

```
Head 1.015   Neck 0.951   Chest 0.714   Spine 0.465   Hips 0.299
```

머리뼈가 키의 81% 에 있고 머리통 반지름이 0.25 쯤이라 아래 끝이 0.765 입니다.
베개 위 끝이 그보다 낮아야 하므로 키의 0.44(0.55, 위 끝 0.78)로 내리고, 앞으로도
더 내밀었습니다 - 위에서 내려다보면 높이 차이보다 **앞뒤 거리**가 가림을
결정합니다.

## 던지는 적이 자기 공을 자기가 받고 있었습니다

큰 아이는 소품을 주워 던지는 적입니다. 그런데 화면에서는 **들고만 다녔습니다.**

찍어 보니 예고는 제대로 돌고 있었습니다.

```
f=20  손에=판다인형  예고=0.47
f=40  손에=판다인형  예고=0.13
f=60  손에=판다인형  예고=-1.00  대기=2.60   <- 던졌는데 아직 손에
```

예고가 끝나고 대기까지 걸렸으니 `_toss` 는 분명히 돌았습니다. 그런데 손이
비지 않았습니다 - **던지자마자 도로 주웠습니다.** 던질 때 소품을 자기 위치에
놓고 속도를 주는데, 다음 프레임에도 아직 몸에서 0.4m 안이라 줍는 거리(1.0m)
안입니다.

날아가는 중인 물건(속도 1.5 초과)은 안 줍게 했습니다. "주운 뒤 몇 초 동안은
안 줍는다" 로 막지 않은 이유: 멈춰 있는 물건은 언제 주워도 되고 날아가는
물건은 누가 던졌든 잡으면 안 됩니다 - **상태로 보는 편이 규칙이 하나**입니다.

같이 고친 것: 소품을 **머리 위가 아니라 손에** 듭니다. 예전 주석에는 "적에게는
드는 자세가 없어서 손 위치를 읽어 봐야 팔이 내려간 자리" 라고 적혀 있었는데,
없으면 만들면 됩니다 - 주인공이 쓰는 자세 층(`CARRY`)을 그대로 걸었습니다.

## 밀린 적이 어디로 밀린 것인지 안 보였습니다

옆에서 밀면 옆으로 미끄러지는데, 몸은 계속 이쪽을 보고 있었습니다. 밀린 것이
아니라 옆으로 걸어가는 것처럼 보입니다.

밀리는 동안 **민 사람 쪽으로 몸을 돌리게** 했습니다. 그러면 적 입장에서는 뒤로
물러나는 것이 되고, 걷기 클립도 **알아서 거꾸로 돕니다** - 원거리 적이 물러날
때 쓰려고 이미 만들어 둔 길(`_moving_back`)이 그대로 맞았습니다. 새로 만든 것은
"어느 쪽을 볼지" 하나뿐입니다.

## 던지기 — 요구를 두 번 잘못 읽었습니다

"적을 잡은 뒤 던지는 것도 밀치는 것과 동일하게 밀려나게 해줘" 를 받고
**힘의 출처만** 맞췄습니다. 밀기 스킬이 던지기에도 붙게 하고 환산 상수를
고쳤지만, 던지는 모양은 그대로 포물선이었습니다.

그 사이에 실제 버그도 하나 나왔습니다. `launch` 가 날아갈 속도를 정해 놓고
마지막 줄에서 `take_damage` 에 **방향까지** 넘겨서, 받는 쪽이 5.0 을 더
얹고 있었습니다(정한 6.0 + 5.0 = 11.0). 밀기에서 한 번 겪은 겹침이 그대로
있었던 것입니다. 그리고 "6.9 로 띄우면 6.0 에서 2.5m" 라는 주석의 실측값이
틀렸습니다 - 다시 재니 4.69m 였습니다. 포물선은 계산으로 나오므로
(체공 시간 = 2 × 높이 ÷ 중력) 재는 대신 계산하게 바꿨습니다.

그래도 답이 아니었습니다. **"밀려난다" 는 바닥으로 밀려난다는 뜻**이었습니다.
세로 움직임을 통째로 없애고 밀기와 같은 방식으로 바꿨습니다 - 바닥을 따라
미끄러지다 멈추고, 다른 것은 세기뿐입니다(2.2배, 3.2m).

놓는 자리도 손 높이가 아니라 있던 자리입니다. 적은 들지 않고 바닥에 끌고
다니는데(`hold_at` 이 발 높이로 내립니다) 놓을 때만 손 높이로 올려서, 세로
속도를 0 으로 만든 뒤에도 0.67m 를 떨어지고 있었습니다.

배운 것: **"A 와 동일하게" 는 값이 아니라 그림을 맞추라는 말일 수 있습니다.**
값만 맞추면 화면에서는 여전히 다른 일이 일어납니다.

## 연타가 언제나 최선이었습니다

기술마다 숨 값을 다르게 잡아 뒀지만(고함 80, 구르기 60, 잡기 10), 그것이
만드는 선택은 **"지금 쓸 수 있나"** 하나뿐이었습니다. 차오르는 대로 같은 버튼을
누르면 되니까요. 특히 밀기는 10 밖에 안 들어 사실상 무한이었습니다.

같은 기술을 1.7초 안에 또 쓰면 처음 값의 절반씩 더 들게 했습니다(2.5배에서
멈춤). **다른 기술로 바꾸면 그 자리에서 처음 값으로 돌아옵니다** - 이 규칙이
하는 말은 "쉬어라" 가 아니라 "섞어 써라" 입니다. 벌금을 물지 않는 길이 항상
열려 있고, 그 길이 게임이 원하는 플레이입니다.

값을 못 쓸 만큼 올리지는 않습니다. 배수를 곱한 값이 최대 숨의 95% 를 넘으면
거기서 멈춥니다 - 그 위로 올리면 비싸진 것이 아니라 **없어진** 기술이 됩니다.

깎는 스킬(「고른 숨」)도 같은 선에서 만들었습니다. **더 드는 몫만** 깎고
(0.5 → 0.3 → 0.1) 0 으로는 못 내립니다. 0 이 되면 연타가 다시 최선이 되어
규칙을 넣은 이유가 사라집니다.

## 붙잡는 아기 — 두 번 틀렸습니다

적 셋(고함 아기·붙잡는 아기·베개 아기)을 넣으면서, 붙잡는 아기만 두 번을
고쳤습니다. 둘 다 **눈으로 봐서는 안 보이고 세어 봐야 보이는** 것이었습니다.

처음 구현은 단순했습니다 — 주인공 등 뒤 0.75m 자리로 걸어가고, 사거리 안에
들어오면 잡는다. 자세와 이펙트까지 다 만들고 확인용 배치(`--pose=cling`)에서는
잘 됐습니다. 그런데 봇 4000프레임을 돌리니 **붙잡힘이 0건**이었습니다.

찍어 보니 이랬습니다.

```
거리=2.16 등뒤=false
거리=1.72 등뒤=false
거리=0.55 등뒤=false
거리=0.40 등뒤=false     <- 몸에 닿았는데도 "앞"
```

**자동 조준 때문이었습니다.** 3.9m 안의 가장 가까운 적으로 조준이 그 자리에서
튀는데, 달려오는 이 아이가 곧 가장 가까운 적이 되므로 다가갈수록 정면에
놓입니다. 등 뒤가 영영 열리지 않습니다. 확인용 배치에서 잘 됐던 것은 거기 적이
하나뿐이라 조준이 굳어 있었기 때문입니다.

그래서 **맴도는 거리를 자동 조준 밖(4.3m)에 두었습니다.** 등이 열릴 때까지
멀찍이 따라다니고, 열리면 속도 ×2.6 으로 파고듭니다. 주인공의 눈이 다른 적에게
가 있는 동안 뒤로 도는 것이 이 적의 정체이므로, 값 하나가 아니라 성격이
정해진 셈입니다.

그래도 0건이었습니다. 이번에는 손 뻗는 자리에서 이유를 찍었습니다.

```
[손뻗음] 못닿음 거리=2.41
```

**예고 0.32초 동안 멈춰 서 있었습니다.** 다른 공격은 예고 동안 멈추는 것이
규칙입니다 - 멈춰야 예고가 읽힙니다. 그런데 주인공은 그 사이 1m 를 달아나므로,
사거리 1.4m 로 시작한 손이 끝날 때는 2.4m 밖에 있습니다. 붙잡기만 예외로 두어
예고 중에도 따라붙게 했습니다. 이 적의 예고는 멈춰 선 몸이 아니라 **달려오는
몸**이라, 예고가 사라지는 것도 아닙니다.

고친 뒤 8층 봇 6000프레임에서 붙잡힘 2건, 풀림 2건 - 남는 것 없이 다 풀립니다.

배운 것 하나: **확인용 배치에서 되는 것과 게임에서 되는 것은 다릅니다.**
`--pose=` 배치는 적이 하나뿐이고 주인공이 가만히 서 있어서, 조준이 어디로
튀는지·주인공이 얼마나 달아나는지가 통째로 빠져 있습니다. 새 적을 넣을 때는
확인용 배치로 규칙을 보고, **실제 소크에서 몇 번 일어나는지 세는** 두 단계가
다 필요합니다.

### 던전

격자 한 칸 1.5m. 겹치지 않게 방을 놓고, 이웃한 방끼리 L 자 복도로 잇고,
고리를 두 개 더 만들어 되돌아 나오는 길이 지루하지 않게 합니다. 시작 방에서 먼
순서로 방을 정렬하므로 **마지막 방이 자연히 가장 깊은 방**이 되고, 거기에 출구를
둡니다.

방은 6~12칸(9~18m), 복도는 2칸(3m)입니다. **이 두 숫자가 사실상 밸런스입니다** —
복도에서는 하나씩 상대하고 방에서는 둘러싸입니다.

길찾기는 `AStarGrid2D` 입니다. 던전이 이미 격자라 내비메시를 굽는 것보다
정확하고, 런타임 베이크에 기대지 않습니다. 시야 판정도 같은 격자 위
브레젠험으로 처리해 물리 레이캐스트를 쓰지 않습니다.

#### 적1_박치기 — 박치기

![박치기 예고](out/screenshot_ram.png)

한 손을 앞으로 뻗어 겨눈 뒤, 그 방향으로 곧장 달려와 부딪힙니다. 맞으면
피해와 함께 **튕겨나갑니다**(밀리는 세기 11, 보통 피격의 두 배가 넘습니다).

| | 기본(적1_박치기) | 큰 적 |
|---|---|---|
| 달리는 거리 | 5.0m | 5.8m |
| 달리는 속도 | 8.0 m/s | 7.0 m/s |
| 예고 | 0.62초 | 0.82초 |
| 밀리는 세기 | 11 | 15 |

**세 값이 하나에서 나옵니다.** 예고로 그리는 길이, 실제로 달리는 거리,
겨누기 시작하는 거리 - 따로 적으면 반드시 어긋납니다. 실제로 처음에는 예고를
2.85m 로 그려 놓고 4.9m 를 달렸습니다. 지금은 `charge_dist` 하나에서
달리는 시간(거리 ÷ 속도)과 예고 길이가 함께 나오고, 겨누기 거리는 그보다
조금 짧습니다(달리다 못 미치는 일이 없도록).

달리는 속도는 걷는 속도에 곱하지 않고 **절대값**입니다. 곱하면 층이 오를수록
같은 예고를 그려 놓고 더 멀리 달립니다.

예고는 발밑의 둥근 고리가 아니라 **길**로 그립니다. 둥근 고리 하나로는 어디로
비켜야 할지 알 수 없습니다 - 앞으로 늘어놓아야 "이 선 위에 서 있지 말라" 가
됩니다. 방향은 예고 시작 순간에 고정되고 예고 중에는 몸도 돌지 않으므로,
옆으로 비키는 것이 확실한 답이 됩니다.

예고 중에 **고정한 방향으로 몸을 돌립니다.** 예고 중에 안 도는 규칙은 "쫓아가느라
계속 따라 도는 것" 을 막으려는 것이지, 이미 정해진 쪽을 보지 말라는 뜻이
아닙니다. 방향을 고정하는 순간의 몸 각도는 조금 전까지 상대를 쫓던 각도라
어긋나 있어서, **옆을 본 채로 앞으로 달려가는** 일이 생겼습니다(실측: 한
번은 79.5도 어긋났습니다). 지금은 예고(0.62초) 안에 다 돌고, 달리는 동안에도
그 방향을 유지합니다 - 부딪히거나 벽에 밀려 몸이 돌아가면 다시 어긋납니다.

한 번 달릴 때 **한 번만** 맞습니다. 닿으면 적도 멈추고 0.45초 휘청입니다 -
뚫고 지나가면 한 번의 돌진이 계속 미는 벽이 되고, 맞은 쪽은 어디서 맞았는지
알 수 없습니다.

닿았는지는 미끄럼 충돌이 아니라 **거리로** 봅니다. 주인공과 적은 서로 밀어
내므로, 닿는 순간에는 이미 조금씩 밀려나 접촉 신호가 한 프레임 뜨거나 두 번
잡힙니다.

#### 자세 — 예고와 돌진

예고는 **다음에 올 것과 닮아야** 합니다. 뻗은 손이 가리키는 쪽이 곧 달려올
쪽이라, 바닥 표시를 못 본 사람도 몸만 보고 비킬 수 있습니다. 한 손만 씁니다 -
두 손을 같이 뻗으면 미는 동작으로 보여서 달려오는 것과 이어지지 않습니다.

돌진 자세의 팔 각도는 **주인공의 고함과 같은 값**입니다. 같은 리그에서 실측으로
고른 "뒤로 벌어진 팔" 이고, 여기서도 하는 일이 같습니다(뒤로 보내서 앞으로
나가는 힘을 그립니다). 다른 것은 머리입니다 - 고함은 젖히고 박치기는
**수그립니다**. 그 차이 하나로 소리를 내는 것과 몸으로 받는 것이 갈립니다.

자세가 실제로 그렇게 되는지는 손 앵커로 쟀습니다(양수가 앞):

```
예고 (f=24~56)   왼손 -0.015   오른손 +0.331   <- 한 손만 앞으로
돌진 (f=64~88)   왼손 -0.246   오른손 -0.241   <- 둘 다 뒤로
```

주인공도 맞으면 자세가 바뀝니다(`PoseOverride.HURT`). 적의 피격 자세와 다르게
만들었습니다 - 적은 소리에 밀려 팔이 벌어지지만, 맞는 쪽이 주인공일 때는
**막는 동작**이 필요합니다. 아무것도 안 하고 젖혀지기만 하면 맞고도 가만히
있는 것으로 보입니다. 팔을 앞으로 모아 얼굴을 가리고 고개를 숙입니다.
붙잡는 시간(0.32초)은 무적 시간보다 짧습니다 - 자세가 무적보다 오래 남으면
이미 움직일 수 있는데 몸은 웅크린 채라 조작이 안 먹는 것처럼 느껴집니다.

#### 붉은 큰 적 — 던지는 아이

예전에는 적1_박치기과 **똑같은 박치기**였습니다(크기와 수치만 달랐습니다). 종류가
넷인데 행동은 셋뿐이었던 셈입니다.

지금은 방에 흩어진 소품을 주워 머리 위로 들고 와서 던집니다. 주인공이 쓰는
기술을 적도 쓰면 규칙이 하나로 읽히고, **소품이 양쪽 모두의 자원**이 됩니다 -
내가 안 쓰면 저쪽이 씁니다.

소품이 없으면 주우러 갑니다(13m 안에서 가장 가까운 것). 그 걸어가는 시간이 곧
예고입니다 - 무엇을 하려는지 몸으로 보입니다. 주울 것이 아예 없으면 그냥
쫓아옵니다. 아무것도 안 하고 서 있으면 고장 난 것으로 보입니다.

던진 소품이 **주인공을 칩니다.** 소품의 피해 판정은 원래 적만 보고 있어서,
누가 던졌는지에 따라 맞는 쪽이 뒤집히도록 고쳤습니다. 물건을 주울 때마다
다시 정합니다 - 적이 던져 놓은 것을 주인공이 주워 던졌는데 그게 주인공을
치면, 물건에 주인이 남아 있는 셈입니다.

죽거나 잡히면 들고 있던 것을 놓습니다. 안 놓으면 소품이 죽은 적을 따라다니거나
아무도 못 줍는 유령이 됩니다.

#### 선생님

3층부터 **출구 방에 한 명만** 섭니다. 뽑기 대상에서 빼 둔 이유는, 한 층에
셋씩 나오면 관문이 아니라 잡몹이 되기 때문입니다. "다 왔다" 싶을 때 마주치게
되고, 체력 260(층 배율 적용)이라 실제로 벽 노릇을 합니다.

주인공의 공격이 소리 지르기라 선생님은 **같은 것을 더 크게** 합니다. 사거리가
두 배가 넘고 각도도 넓지만, 그만큼 예고가 깁니다(0.9초).

![선생님의 호통 예고](out/screenshot_teacher.png)

예고에서 중요한 것은 **방향이 시작 순간에 고정된다**는 점입니다. 예고 내내
방향이 따라오면 옆으로 굴러도 소용이 없어 그냥 "맞거나 멀리 있거나"가 됩니다.
고정해 두었기에 옆으로 빠지는 것이 정답이 되고, 그래서 다른 적들과 대처법이
겹치지 않습니다. 위험 구역은 그 방향으로 늘어놓은 고리가 그려 줍니다 -
둥근 고리 하나로는 어디로 피할지 알 수 없습니다.

원거리 적만 다른 메시를 씁니다. 크기와 색조로도 구분되지만 **가장 먼저 알아봐야
하는 적**이라 실루엣(양갈래 vs 땋은 머리)까지 다르게 뒀습니다.

셋이 한 방에 섞이면 "누구부터 처리할지"라는 판단이 생깁니다. 그 판단이 없으면
적이 몇이든 같은 싸움입니다.

공격에는 반드시 **예고**가 있습니다(몸이 번쩍이고 바닥에 붉은 고리). 예고 없이
맞는 피해는 배울 수가 없습니다.

적은 보이고 가까울 때만 깨어납니다. 층 전체가 한꺼번에 몰려오면 방을 하나씩
정리하는 리듬이 사라집니다.

### 소리

넷입니다. 둘은 녹음이고 둘은 합성입니다.

| | 파일 | 언제 |
|---|---|---|
| 고함 | `shout_a1.wav` (vtos 클립) | 지르는 순간 |
| 밀치기 | `push_a2.wav` (vtos 클립) | **누르는** 순간 |
| 잡기 | `grab_pop.wav` (합성) | 손에 붙는 순간 |
| 던지기 | `throw_whoosh.wav` (합성) | **놓는** 순간 |

고함과 밀치기는 같은 아이의 목소리(a1/a2)라, 두 기술이 한 사람의 것으로
들립니다.

잡기와 던지기는 쓸 만한 녹음이 없어 `tools/make_sfx.py` 로 만들었습니다.
잡기는 440→990Hz 로 휘어 올라가는 짧은 "뽕"(올라가는 쪽이 "붙었다", 내려가면
"놓쳤다" 로 들립니다), 던지기는 저역통과 문턱이 올라가는 바람 소리 위에
휘파람을 얹은 것입니다. 둘 다 장조 음정으로 잡았습니다 - 같은 합성이라도
반음이 섞이면 불길해집니다.

**언제 내는지가 절반입니다.** 밀치기는 판정(0.23초 뒤)이 아니라 **누르는
순간**에 냅니다 - 판정에 맞추면 버튼과 소리 사이가 벌어져 조작이 굼떠집니다.
클립 자체가 0.3초에 걸쳐 부풀어서 가장 큰 지점이 판정 근처에 옵니다.
반대로 던지기는 예비동작이 아니라 **손을 떠나는 순간**입니다 - 먼저 내면
아직 손에 있는데 날아가는 소리가 납니다.

적이 던질 때도 같은 소리를 **8dB 낮춰** 냅니다. 날아오는 것을 화면 밖에서도
알아채야 하는데, 같은 크기면 누가 던졌는지 헷갈립니다.

동시에 낼 수 있는 소리를 넷에서 여섯으로 늘렸습니다. 소리가 하나에서 넷으로
늘면서, 밀치기 한 번에 고함과 잡기가 겹치면 앞의 것이 끊겼습니다.

### 성장

층을 정리하면 축복 셋 중 하나를 고릅니다. 같은 계열이 한 번에 둘 나오지 않도록
묶어서 뽑으므로, 선택지가 늘 다른 방향을 가리킵니다.

![축복 고르기](out/screenshot_boon.png)

#### 수치를 올리는 축복과, 규칙을 바꾸는 축복

처음 아홉 개는 전부 숫자를 올렸습니다(공격력, 체력, 속도, 치명타…). **무엇을
골라도 같은 방식으로 싸우게 되므로**, 다시 도전할 때 "이번엔 다르게 풀린다" 가
생기지 않습니다.

그래서 네 개를 더했습니다. 각각 **이미 만들어 둔 시스템 하나**에 걸려 있어서,
뽑히는 순간 그 시스템을 쓰는 판이 됩니다.

| 축복 | 무엇이 바뀌나 | 어디에 걸렸나 |
|---|---|---|
| 돌풍 | 고함이 적을 밀어냅니다 (돌진도 끊습니다) | 고함 판정 |
| 폭죽 놀이 | 던진 소품이 터집니다 (3m, 피해 0.55배) | 소품 던지기 |
| 구르는 돌 | 구르며 뚫고 지나가며 칩니다 (0.6배) | 구르기 |
| 메다꽂기 | 던진 적이 떨어지며 주변을 굳힙니다 (2.8m) | 적 던지기 |

**계열(`trick`)을 따로 뒀습니다.** 기존 계열에 넣으면 서로를 밀어내서 뽑힐
확률이 반으로 줍니다. 성격을 바꾸는 축복은 한 판에 하나쯤 나와야 그 판의
색이 됩니다 - 지금 배치에서 셋 중에 뜰 확률이 **80%** 입니다(계열 구성으로
2만 번 모의).

**켜짐/꺼짐이 아니라 수치**로 뒀습니다. 같은 축복을 두 번 뽑으면 쌓입니다.
bool 이면 두 번째는 아무 일도 안 일어나는데, 그때가 하필 셋 다 마음에 안 드는
판입니다.

값은 조심스럽게 잡았습니다. 구르기는 이미 무적이라 피해까지 세면 "굴러다니기만
하면 되는" 판이 되고, 폭발이 직격보다 세면 아무렇게나 던지는 것이 답이 됩니다 -
터지는 것은 **여럿을 건드리는** 수단이지 더 아픈 수단이 아닙니다.

상인은 2층부터 나옵니다(1층에는 쓸 금화가 없습니다). 재고 셋 중 하나는 항상
회복약입니다 — 살 것이 공격력뿐이면 상점이 함정이 됩니다. 가격은 층마다
오릅니다.

## 개발용 인자

```
run.bat --bot                 자동 플레이. 층 전환·축복·상점·죽음까지 혼자 지나갑니다
run.bat --boon=gale,bomb       축복을 미리 걸고 시작. 뽑기를 기다리면 확인이 안 됩니다
run.bat --shoulder            어깨 너머 시점으로 시작
run.bat --ui=riglab --char=1 --clip=Walk --motion=0.6
                              리그 실험실을 그 캐릭터/동작/배율로 바로 엽니다
run.bat --floor=5             5층부터(그만큼 축복을 받은 상태로)
run.bat --ui=boon|shop|death|title|help    해당 화면을 바로 띄우기
run.bat --shot=C:\out.png --shot-frame=180 몇 프레임 뒤 화면을 파일로
run.bat --seed=4242           같은 던전을 다시 불러오기(버그를 두 번 보려면 필수)
run.bat --quit-after=2400     N 프레임 뒤 종료(무사히 지났는지 확인)
run.bat --cam=0.3 --face=180  카메라 배율 / 조준 고정. 모델 방향 확인용
run.bat --pose=run|roll|shout|hold|drag|pitch  그 동작만 계속 시킵니다
                              (pitch: 표적을 세워 두고 던져 맞히기)
run.bat --pitch=25            카메라를 눕혀 벽면·자세를 정면에서 보기
run.bat --no-toon             카툰 렌더링을 끈 채로 시작(비교용)
run.bat --die-at=300          그 프레임에 쓰러뜨립니다. 랙돌 확인용
run.bat --touch               데스크톱에서 폰 조작 화면을 띄웁니다
run.bat --teacher-here        선생님을 시작 방에 세웁니다(호통 확인용)
run.bat --fps-log             1초마다 최악 프레임 시간
run.bat --trace-at=4200       그 프레임의 카메라/플레이어 상태
```

녹화는 브라우저 안에서만 도는 기능이라 위의 어떤 인자로도 확인되지 않습니다.
진짜 크롬을 띄워 확인하는 것이 따로 있습니다:

```
python tools\serve.py                                  (다른 창에서)
npm install playwright-core
node tools\web_probe.mjs http://127.0.0.1:8807/ out\web
```

제목 버튼으로 판을 시작하고, 몇 초 놀고, 게임 안 저장 버튼으로 끝낸 뒤 **결과
영상을 한 프레임 그려 밝기를 셉니다.** 이 기능의 실패는 대개 조용하기 때문입니다 -
검게 녹화돼도 파일 크기는 멀쩡하고, 소리가 빠져도 재생해 보기 전에는 모릅니다.
컨테이너를 열어 소리 트랙이 있는지도 보고, **연달아 두 번** 찍습니다(정지할 때
소리 갈래까지 끊으면 두 번째부터 무음이 됩니다).

`--bot` 은 잘 싸우는 봇이 아닙니다. **모든 화면을 한 번씩 지나가게** 하는 것이
목적입니다. 화면을 보지 않고도 흐름이 끊긴 곳을 찾을 수 있습니다.

## 내보내기

웹은 바로 됩니다(`tools\build_web.bat`). 템플릿이 설치돼 있고, 렌더러 전환과
글꼴 번들도 프로젝트에 들어 있습니다.

Windows 실행 파일 프리셋도 `export_presets.cfg` 에 있지만 이 PC 에는 **웹용
템플릿만 설치돼 있어** 지금은 안 됩니다. 에디터의
`편집기 > 내보내기 템플릿 관리`에서 Windows 템플릿을 받으면 그대로 됩니다.

```

## 알려진 한계

- **상인만 화풍이 다릅니다.** 주인공과 적은 새 아이들로 갈아 끼웠지만 상인은
  아직 이전 원화(불꽃 깃털 계열)입니다. 같은 결의 3면도를 하나 더 주시면
  `tools/make_kids.py` 에 한 줄 추가로 끝납니다.
- 적이 아이 모습입니다. 설정상 어색하면 `enemy.gd` 의 `KINDS` 에서 메시만
  바꾸면 됩니다.
- 축복은 전부 수치 증가입니다. 규칙을 바꾸는 축복(관통, 반사 같은)은 없습니다.
- 랙돌을 만들 때 엔진이 `p_bone = -1` 오류를 본 개수만큼 한 번 뱉습니다.
  `PhysicalBone3D` 의 본 번호가 트리에 들어간 뒤에야 정해지는데 생성 중에
  조회되기 때문입니다. 동작에는 영향이 없습니다.
- 크롬(PC·헤드리스)에서는 게임 화면이 뜨고 녹화·내려받기까지 도는 것을
  확인했습니다(`tools/web_probe.mjs`). **아이폰 사파리에서는 확인하지
  못했습니다** - 손에 기기가 없습니다. 사파리는 `MediaRecorder` 와
  `captureStream` 을 늦게 받아들인 브라우저라, 안 되면 제목 화면의 녹화
  버튼이 아예 안 나오고 그 자리에 이유가 적힙니다(게임은 그대로 됩니다).
- 녹화한 영상을 **메신저로 실제로 보내 본 것은 아닙니다.** 만들어지는 파일이
